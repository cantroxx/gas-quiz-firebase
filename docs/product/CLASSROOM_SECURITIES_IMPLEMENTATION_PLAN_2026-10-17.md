# 우리 교실 증권 — 퀴즈타운 구현 작업 예상안

작성일: 2026-10-17 (Asia/Seoul)  
대상 저장소: `gas-quiz-firebase`  
문서 성격: 다음 Codex 작업에 전달할 제품 명세·구현 계획·검증 기준  
상태: **설계 제안. 구현·운영 재화 연결·배포 완료를 뜻하지 않는다.**

## 1. 구현할 결과

퀴즈타운 **우리 교실 → 경제 → 증권**에 초등 4학년용 모의 주식시장을 추가한다. 학생이 기업과 뉴스를 읽고, 투자 이유를 작성하고, 가상 주식을 매매한 뒤 결과를 돌아보게 한다. 기존 퀴즈·직업·마켓·은행·방 꾸미기와 같은 계정으로 이용한다.

핵심 경험은 `뉴스 읽기 → 기업 비교 → 이유 작성 → 주문 확인 → 매매 → 투자일지 복기`다. 성과를 돈의 크기나 순위만으로 평가하지 않는다.

- 화면 이름: **우리반 증권소**. 메뉴 이름: **증권**.
- 첫 구현은 합성 데이터와 Emulator 기반 연습 시장까지 완성한다.
- 최종 연결안은 **DJ코인 지갑 ↔ 증권 예수금**이다. 교실 포인트와 직접 교환하는 새 통로는 만들지 않는다.
- 실제 DJ코인 연결, 학생 기록 저장, 보안 규칙 변경과 운영 배포는 저장소 승인 규칙에 따라 별도로 진행한다.
- 참고 서비스의 기능 개념을 분석한 자체 구현이다. 그라운드에 iframe을 붙이거나 계정·데이터·비공개 API를 연결하는 작업이 아니다.

## 2. 조사 근거와 확인 범위

### 2.1 참고 서비스에서 직접 확인한 사실

2026-10-17 로그인된 [그라운드 카드 화면](https://growndcard.com/cards)의 증권 관리 및 교사 예시 계좌를 읽기 전용으로 확인했다.

- 자동 관리 가상 기업 20개, 위험도·업종·기업 규모, 주가 차트, 배당 안내.
- 시장 지수·시총가중 지수·시가총액 지도.
- 공식 발표·업계 소식·소문 정정 뉴스와 교사 뉴스 발행.
- 예수금, 매수·매도, 수수료·세금, 거래 횟수·종목 비중·입금 제한.
- 거래일지와 매수 이유, 현재 보유분 평가수익률을 기준으로 하는 상위 5명 표시.
- 학생 포인트 활동에 연동되는 공동체 기업 기능.

가격 알고리즘·권한 검증·실제 주문 처리·복구 동작은 확인하지 않았다. 학생 이름·잔액·거래 내역을 본 문서나 fixtures에 복제하지 않는다. 아래 수치와 산식은 **퀴즈타운용 제안**이며 그라운드의 내부 구현에 대한 설명이 아니다. 기업명·뉴스 문안·이미지·코드를 복제하지 않는다.

## 3. 범위와 단계

| 단계 | 포함 | 완료 기준 |
| --- | --- | --- |
| A. 로컬 시제품 | 경제 메뉴 연결, 12개 기업, 시장·종목·계좌·뉴스·일지 UI, 합성 계좌, 순수 계산 로직 | 서버 없이 화면과 학습 흐름을 검토 가능 |
| B. 서버 MVP | 인증·학급 범위, 연습 계좌, 일별 시세, 뉴스, 매매·원장·제한·교사 제어, Emulator 검증 | 중복·동시 주문과 권한 테스트 통과, 운영 연결 전 리뷰 가능 |
| C. DJ코인 연결 | 원자적 입출금, 기존 지갑 호환, 경제 회귀 검사, 통화 공급 제한 | 승인된 환경에서 보존식·장애 복구 검증 |
| D. 운영 도입 | 명시 승인 후 한 학급 시범, 기능 플래그·모니터링·배포 보고 | 수업 1회 이상 점검 후 확대 여부 결정 |
| E. 후속 확장 | 배당, 시총 지도, 누적 성과 비교, 공동체 기업 | 별도 명세·경제 영향 검토 후 진행 |

**MVP에 포함하지 않는 것:** 학생끼리 주문을 맞추는 거래소, 지정가·예약 주문, 공매도·대출·레버리지·파생상품, 실시간 외부 시세, 현금 결제, 학생 기업 설립, 자동 뉴스 생성 AI, 주식 수익에 대한 XP·랭킹 보상, 자동 시즌 초기화.

거래 상대는 시스템이다. 발행주식수는 회사 규모 설명용이며, MVP에서 학생 수요로 가격이 움직이거나 실제 발행물량이 소진되는 구조는 아니다. 화면 도움말에 이 단순화를 명시한다.

## 4. 화면과 사용 흐름

### 4.1 우리 교실 연결

- `CLASSROOM_GROUPS.economy`에 `securities` 추가.
- 기존 경제 내비게이션에 증권 버튼을 같은 위계로 연결한다. `classroom-workspace.js`의 버튼 이동·재구성·숨김 조건을 함께 확인한다.
- 패널은 `data-classroom-panel="securities"`, 기본 ID는 `classroom-securities-panel`로 제안한다.
- 증권 전용 데이터는 증권 진입 시 불러온다. 교실 홈·마켓·은행 진입에 증권 API 호출을 추가하지 않는다.
- 증권에서 돌아와도 경제 메뉴·스크롤·선택 상태가 일관되게 유지되어야 한다.
- 기능이 꺼진 학급에서는 메뉴를 숨기고, 직접 호출도 서버에서 차단한다.

### 4.2 학생 화면

증권 상단은 `시장 상태 / 시세 기준일 / 모드(연습 또는 DJ코인 연결)`을 표시하고, `예수금 / 주식 평가액 / 누적 손익`을 보여준다. 기능 내부 메뉴는 **시장·뉴스·내 계좌·투자일지** 네 개로 제한한다.

| 화면 | 필수 구성 |
| --- | --- |
| 시장 | 기업명, 업종, 위험도, 현재가, 전 거래일 대비 등락, 보유 표시, 검색·정렬 |
| 종목 상세 | 회사 소개, 영향을 주는 경제 요인, 최근 20거래일 종가 선형 차트, 관련 뉴스, 내 보유분, 매수·매도 |
| 주문 확인 | 수량, 가격 기준일/버전, 거래금액, 수수료, 예상 세금, 거래 후 예수금, 매수 이유, 최종 확인 |
| 뉴스 | 날짜·출처 유형·관련 업종, 본문, 정정 연결. 미래 뉴스 효과 수치와 서버 난수는 표시하지 않음 |
| 내 계좌 | 보유 수량·평균 원가·평가손익, 예수금, DJ코인 입출금, 누적 입출금·수수료·세금 |
| 투자일지 | 매수 이유, 체결 결과, 사후 돌아보기. 본인·담당 교사만 조회 |

연습 모드에서는 입출금 UI를 제거하고 “연습머니는 DJ코인으로 바꿀 수 없어요”를 표시한다. 계좌가 없으면 조회만으로 만들지 말고 **연습 계좌 시작** 버튼으로 명시 생성한다.

모바일은 목록 → 상세 → 주문 순서의 한 열 화면을 사용한다. 기존 교실의 색·글꼴·버튼을 재사용하고 증권만 별도 금융 앱처럼 만들지 않는다. 390px·768px·1440px에서 검증하고, 색 외에도 상승/하락 기호와 텍스트를 제공한다. 모달 포커스·Escape·닫은 후 포커스 복귀, 터치 대상 44px 이상, 로딩·빈 화면·실패·재시도 상태를 포함한다.

### 4.3 교사 화면

- 현재 상태, 다음 개장 시각, 시세 생성 성공/실패, 활성 계좌 수와 합계.
- 기능 활성화, 수동 거래 중지, 거래 시간·휴장일·제한 설정. 저장 시 설정 버전과 변경 사유 기록.
- 뉴스 초안·예약·발행·정정. 발행한 뉴스의 가격 영향은 소급 변경하지 않는다.
- 학생 계좌·거래·투자 이유 조회. 담당 학급 안에서만 허용.
- 원장 불일치 **조회 보고서**. 자동 잔액 복구 버튼은 MVP에 넣지 않는다.
- 초기화·일괄 지급·전액 환급은 기본 관리 UI에서 제공하지 않는다.

## 5. 경제·거래 규칙 제안

아래는 로컬·Emulator에서 구현할 기본값이다. 실제 DJ코인 연결 전에는 학급의 재화 수급을 확인하여 승인받는다.

| 항목 | 제안 기본값 |
| --- | --- |
| 연습 시작 금액 | 1인 1,000 연습머니, 시장별 1회 지급 |
| 실제 재화 모드 시작 금액 | 0. 기존 DJ코인을 학생이 입금해야 이용 가능 |
| 교환 비율 | 1 DJ코인 = 1 증권 예수금. 시장 생성 후 변경 불가 |
| 금액 정밀도 | 내부 1/100 단위 정수, 표시 소수 둘째 자리까지 |
| 주문 수량 | 정수 1주 이상, 주문당 최대 100주 |
| 거래 시간 | 평일 09:30 이상 14:30 미만, Asia/Seoul. 교사가 휴장일 지정 |
| 가격 갱신 | 거래일당 1회, 개장 시 새로운 시세 공개 후 당일 고정 |
| 뉴스 공개 | 거래일 08:30. 당일 가격 반영 전까지 전일 가격 거래 금지 |
| 매매 횟수 | 체결 성공 기준 1인 하루 총 3회 |
| 수수료 | 매수·매도 각 거래금액의 0.5%, 소수 셋째 자리에서 반올림하여 둘째 자리까지 |
| 매도차익세 | MVP 0%. 후속 승인 시 별도 도입 |
| 한 종목 최대 비중 | 매수 직후 증권 순자산의 50%, 예수금 포함 |
| DJ코인 하루 입금 한도 | 100코인, 해당 KST 날짜의 총입금 기준. 출금해도 한도 복원 안 됨 |
| DJ코인 누적 순입금 한도 | 300코인. `max(0, 누적 입금 - 누적 출금)` 기준 |
| 증권 순자산 상한 | 500코인. 입금·매수는 초과 예상 시 거부, 상승으로 초과해도 강제 매도 없음 |
| 매수 이유 | 공백 제거 후 10~200자, 필수. 서버 재검증 |
| 공개 투자 순위 | MVP 없음. 개인 성과와 반 전체 익명 요약만 제공 |

DJ코인 입금·순입금 한도와 순자산 500코인 상한은 **실제 재화 모드에만** 적용한다. 연습 모드는 입출금 없이 초기 1,000 연습머니로 시작하며 순자산 상한은 두지 않는다. 거래 횟수·비중·수수료·매수 이유 규칙은 두 모드에 동일 적용한다.

비중은 `매수 후 해당 종목 평가액 ÷ 매수 후 (예수금 + 전체 주식 평가액)`으로 계산한다. 수수료를 차감한 뒤 판정하며, 분모가 0이면 매수를 거부한다. 첫 매수도 동일 규칙을 적용한다. 예수금 100, 주가 20, 1주 매수 수수료 0.10이면 비중은 `20 / 99.90`으로 허용된다. 잔액 부족·비중 초과 시 사유와 구매 가능한 최대 수량을 보여주고 규칙을 우회하지 않는다.

학생은 보유 수량 이내에서만 매도하고 잔액 이내에서만 매수한다. 거래 중지·휴장 중에도 조회와 정상 예수금 출금은 허용한다. 단, 계좌 무결성 이상으로 별도 동결한 계좌의 쓰기는 차단하고 교사 안내를 제공한다.

### 5.1 정수 처리와 손익 산식

금액 필드는 예를 들어 `cashMinor`, `priceMinor`로 구분한다. 1코인은 100 minor다. 수수료는 basis point 정수로 저장하고 곱셈·합산 결과가 안전한 정수 범위인지 검증한다. 음수·NaN·Infinity·초과 자릿수·문자열 강제 변환을 주문 입력으로 허용하지 않는다.

- 매수 총액 = `가격 × 수량 + 수수료`. 이 금액을 보유 원가에 더한다.
- 매도 배분 원가 = `floor(기존 원가 × 매도 수량 / 기존 수량)`. 전량 매도 시 잔여 원가 전액을 배분한다.
- 실현 손익 = `매도금액 - 매도수수료 - 세금 - 배분 원가`.
- 미실현 손익 = `현재 주식 평가액 - 잔여 보유 원가`. 향후 매도 비용은 포함하지 않음을 표시한다.
- 순자산 = `예수금 + 주식 평가액`.
- 누적 손익 = `순자산 + 누적 출금 - 누적 입금 - 연습 초기지급액`.
- 입출금은 이익·손실로 계산하지 않는다. 수수료·세금은 누적 손익에 이미 포함되므로 다시 빼지 않는다.
- 누적 성과율은 MVP에서 제공하지 않는다. 입출금 시점을 무시한 수익률이나 현재 보유분 수익률을 전체 성과로 표시하지 않는다.

DJ코인 입출금은 정수 코인만 허용한다. 예수금 12.34일 때 출금 가능한 최대치는 12코인이며 0.34는 계좌에 남는다. 소수 잔액을 반올림해 지갑에 지급하지 않는다. 지갑의 기존 정수 단위를 바꾸지 않는다.

검산 예: 100을 입금 → 20짜리 2주 매수(수수료 0.20) → 가격 22에 1주 매도(수수료 0.11)하면 예수금 81.69, 잔여 원가 20.10, 평가액 22, 실현손익 1.79, 미실현손익 1.90, 누적손익 3.69다. 이후 10 출금 시 순자산 93.69와 누적손익 3.69가 유지되어야 한다.

### 5.2 경제 영향과 재화 공급

시스템 상대 거래는 주가 상승 이익을 출금할 때 DJ코인을 추가 공급할 수 있다. 단순한 지갑 간 이동만으로 전체 경제 보존이 성립한다고 주장하면 안 된다.

- 입출금 자체는 `기존 지갑 변화 × 100 + 예수금 변화 = 0`이어야 한다.
- 거래에는 예수금·보유 원가·수수료 적립·시장 손익 상대 계정을 연결한 변경 불가능 원장을 남긴다.
- 실제 재화 모드에서는 수수료를 증권 전용 준비금에 쌓는다. 기존 교실 세금/공동기금으로 임의 합산하지 않는다.
- 일별 보고서는 총입금·총출금·실현손익·수수료·평가손익을 분리한다. 투자 이익을 퀴즈 보상으로 기록하거나 포인트 미러링 함수를 호출하지 않는다.
- 실제 모드의 누적 순유출 예산은 학급당 1,000 DJ코인을 제안한다. 예산 초과 시 **신규 입금·매수**를 중지하고 교사에게 알리되, 기존 보유분 매도·정상 출금은 허용한다. 이는 손실 상한 보장이 아니라 추가 노출 억제 기준이다.
- 실제 연결 전 20·60·120거래일의 하락/횡보/상승 시나리오로 유통량 영향을 보고한다. 허용하기 어렵다면 연습 모드로 유지한다.

### 6.2 일별 시세 엔진

서버에서만 계산한다. 초기 제안은 다음과 같다.

1. 거래일별 공통 시장 요인 -50~+50bp.
2. 업종별 요인 -50~+50bp.
3. 기업별 변동: 낮음 ±100bp / 보통 ±200bp / 높음 ±300bp.
4. 당일 유효한 뉴스 효과: 약 ±100bp / 중 ±200bp / 강 ±300bp. 기업/업종/시장 범위를 명시.
5. 합계 변동을 ±500bp(±5%)로 제한하고 가격을 계산한다. 가격은 1.00 이상, 1,000.00 이하. 가격 하한·상한·반올림 때문에 실제 표시 변동률은 산식 목표와 다를 수 있다.

무작위 요인은 `marketId + tradingDate + 종목/업종 + algorithmVersion`에 서버 전용 seed를 결합하여 재시도해도 같은 결과를 얻도록 한다. seed·미래 가격·미발행 뉴스 효과는 클라이언트에 내보내지 않는다. 테스트에서는 seed와 시계를 주입한다. 계산 과정·입력 뉴스 ID·알고리즘 버전을 서버 감사 자료로 보관한다.

당일 시세는 **한 번 공개하면 불변**이다. 교사의 재실행도 동일 결과를 반환하고 덮어쓰지 않는다. 새 데이터에 따른 재가격은 다음 거래일에만 적용한다. 학생 거래량에 따라 가격이 변하지 않는다는 점을 도움말에 적는다.

일별 종가만 생성하므로 MVP는 선형 차트를 사용한다. 시가·고가·저가를 생성하지 않았는데 캔들 차트를 만들어 실제 관측값처럼 보여주지 않는다.

### 6.3 일정·장 상태·실패 처리

- 뉴스 발행과 시세 생성을 별도 예약 작업으로 분리하되, 개발·Emulator에서는 같은 서비스를 명시 호출할 수 있게 한다.
- 시장 운영 모드(`disabled / enabled / paused / archived`)와 서버 산출 세션 상태(`preopen / open / closed / holiday / error`)를 구분한다.
- 유효 거래 조건: 활성화 + 서버 시각이 시간 내 + 휴장 아님 + 당일 시세 공개 완료 + 계좌 쓰기 허용.
- 모든 화면은 서버가 돌려준 동일한 거래 시간·상태 문구를 사용한다. 클라이언트 시계는 카운트다운용일 뿐 거래 허가 근거가 아니다.
- 당일 시세 생성이 실패하면 거래를 열지 않는다. 마지막 성공 시세는 날짜와 함께 열람만 허용한다.
- MVP 12개 기업 시세를 한 문서에 묶어 제한된 크기로 생성하고, 준비 완료 후 시장 포인터를 원자적으로 전환한다. 부분 생성된 종목이 거래에 노출되지 않게 한다.
- 이전 거래일이 누락되면 임의로 건너뛰거나 무제한 catch-up하지 않는다. 시장을 error 상태로 유지하고 누락 순서대로 같은 엔진을 재실행하는 복구 보고서를 제공한다.
- 금요일 이후 주말·휴장일에는 “개장 전” 대신 휴장과 다음 거래일을 표시한다.

### 6.4 뉴스

- MVP는 사전에 작성한 교육용 템플릿 30개 이상과 교사 작성 기능을 사용한다. 외부 웹 수집·LLM 호출을 필수 의존성으로 넣지 않는다.
- 기본 주제: 원재료 가격, 날씨, 신제품, 소비 변화, 공공시설, 에너지 비용, 정보 정정.
- 뉴스에 공개 시각·효과 적용 거래일·관련 기업/업종·정정 원문 ID를 저장한다.
- 당일 08:30 이후 등록한 가격 영향 뉴스는 다음 거래일로 예약한다. 이미 공개한 시세를 소급 변경하지 않는다.
- 학생에게 방향을 생각할 근거를 주되 정확한 bp·미래 결과를 공개하지 않는다.
- 뉴스 효과는 결정적 매수 신호가 아니라 다른 변동 요인과 합산된다. 소문에는 불확실성을 명시하고 정정과 복기 질문을 짝지어 작성한다.

## 7. 데이터 설계 제안

모든 신규 경로는 **제안**이다. 구현 직전 실제 컬렉션 충돌·권한·인덱스를 확인한다. 학급 루트의 기존 스키마와 `userEconomy`를 교체하지 않는다.

기본 루트: `classrooms/{classId}/securitiesMarkets/{marketId}`. `marketId`는 연습/실제 재화 시장을 명확히 분리하는 불변 ID다. 시장의 `mode`를 나중에 바꾸지 않는다. 연습 계좌를 실제 계좌로 전환·복사하지 않는다.

| 문서/하위 경로 | 주요 필드 |
| --- | --- |
| 시장 문서 | mode, lifecycle, configVersion, algorithmVersion, currentPriceVersion, sessionSchedule, holidayDates, limits, feeBps, currencyScale |
| `companies/{companyId}` | 이름, 소개, 업종, 위험도, 초기가, 발행주식수, 활성 상태 |
| `dailyPrices/{YYYY-MM-DD}` | 거래일, version, 이전 버전, 기업별 가격·등락, 공개 시각. 공개 후 불변 |
| `privateEngine/{dateKey}` | seed 식별자, 요인·뉴스 효과, 생성 상태·검증 요약. 서버 전용 |
| `news/{newsId}` | 제목·본문·범위·유형·발행 시각·적용일·정정 연결·버전. 학생 응답은 공개 필드만 |
| `accounts/{memberUserId}` | cashMinor, depositsMinor, withdrawalsMinor, initialGrantMinor, realizedPnlMinor, feesMinor, revision, status |
| 계좌의 `positions/{companyId}` | quantity, costBasisMinor. 평균가는 계산값 |
| 계좌의 `dailyLimits/{dateKey}` | 체결 횟수, 총입금. 서버 KST 날짜 기준 |
| 계좌의 `operations/{requestId}` | 정규화 payloadHash, 작업 유형, 서버 확정 결과, 처리 시각. 중복 처리 방지 |
| 계좌의 `ledger/{entryId}` | 입출금·매매·지급·조정의 전후 금액·수량·원가, 시세/설정 버전, 연결 ID. 불변 |
| 계좌의 `journal/{tradeId}` | 원래 매수 이유 참조, 사후 성찰, 교사 피드백. 수정 이력/버전 |
| `treasury/current` | 누적 수수료·세금, 시장 상대 계정 집계, 순유출 경고 상태 |
| `adminAudit/{eventId}` | 행위자, 사유, 이전/이후 설정, 요청 ID, 시각 |

교사의 계좌 목록은 페이지 단위로 조회하고 학생 API에는 본인 계좌만 반환한다. 관리자 감사 로그·미발행 뉴스·미래 가격을 공개 시장 응답에 섞지 않는다. 클라이언트 필터링으로 보안을 대신하지 않는다.

초기 전체 증권 데이터 접근은 검증된 callable을 통하게 하고 Firestore 클라이언트 직접 읽기·쓰기는 거부하는 안을 우선한다. Admin SDK는 Rules를 통과하지 않으므로 서비스 자체에서 회원·학급·역할을 검증한다. 기존 광역 match가 신규 경로에 접근을 열지 않는지도 실제 Rules 테스트로 확인한다.

## 8. 서버 API·거래 무결성

제안 callable은 `classroomSecuritiesQuery`, `classroomSecuritiesAction`, `classroomSecuritiesAdminAction`이다. `functions/index.js`는 기존 인증 헬퍼를 주입하고 export만 연결하며, 본문은 별도 모듈에 둔다.

| API | 액션 | 요구 사항 |
| --- | --- | --- |
| Query | market, company, news, account, ledger, journal | 조회에 계좌 생성·보상·시세 생성 등 쓰기 부수효과 없음. 페이지 상한·cursor |
| Action | openAccount, deposit, withdraw, buy, sell, reflect | 계정·학급 검증, 변경 요청 ID, 입력 검증, 명확한 오류 |
| AdminAction | updateSettings, pause, resume, saveNews, publishNews, audit | 담당 학급 교사 검증, revision 충돌 검사, 사유·감사 이력 |
| 서버 작업 | publishScheduledNews, generateDailyPrices | 공개 callable로 학생이 실행 불가. 작업 재실행 멱등성 |

### 8.1 인증

`request.auth.uid`와 기존 `assertLinkedMemberAuth`로 실제 회원 연결을 검증한 뒤 `loadClassroomSettingsForTransaction`과 `assertMemberCanEnterClassroom`을 적용한다. `memberUserId`·`classId`·교사 여부를 브라우저 주장만으로 신뢰하지 않는다. 교사 작업에는 담당 학급 관리 권한을 추가 검증한다. 동일 권한 기준을 query와 action 모두에 적용한다.

### 8.2 중복·동시 주문

1. 클라이언트는 사용자 확정 의도마다 UUID `requestId`를 만들고 네트워크 재시도에는 그대로 사용한다.
2. 서버는 시장·계좌·액션·정규화된 입력을 묶어 payloadHash를 저장한다. 같은 ID와 같은 payload면 저장된 결과를 반환하고, 다른 payload면 충돌 오류를 반환한다.
3. 인증 후 이미 성공한 요청인지 먼저 확인한다. 다음날 재시도라도 과거 성공 결과를 돌려주며 다시 거래하지 않는다.
4. 신규 주문은 같은 Firestore transaction 안에서 시장 설정·시세 버전·계좌·전체 12개 보유분·일별 한도·요청 기록·준비금을 읽고 검증한다. 모든 읽기를 쓰기보다 먼저 수행한다.
5. 예수금·보유량·원가·한도·원장·준비금·성공 결과를 함께 커밋한다. 잠정 UI 결과를 확정 잔액으로 저장하지 않는다.
6. 주문에 `expectedPriceVersion`을 포함한다. 새 시세로 바뀌면 자동 가격 대체 대신 재확인을 요구한다.
7. 매매·출금·마켓 구매가 동시에 일어나도 잔액이 음수가 되지 않게 동일 권위 지갑 문서를 transaction으로 읽고 쓴다.

중복 방지 기록은 원장과 함께 보존한다. 계좌가 살아 있는데 TTL로 지우고 오래된 요청의 재실행을 허용하지 않는다. 요청 제한과 계좌/학급별 쓰기 충돌은 단일 학급 규모에서도 부하 테스트한다.

### 8.3 DJ코인 연결 시 필수 확인

- 현재 코드의 `djCoin`·레거시 `coin` 호환을 조사한다. `coin`만 있는 문서에 `djCoin: increment(-amount)`를 적용하여 기존 잔액을 잃는 구현을 금지한다.
- canonical 잔액을 읽고 새 `djCoin` 값을 명시적으로 쓰는 방식 등, 기존 구매·환전과 일관된 정책을 결정한다. 기존 문서를 일괄 마이그레이션하지 않는다.
- 지갑 차감/증가, 증권 예수금 반대 방향 변경, 양쪽을 연결하는 원장·멱등 결과를 **동일 transaction**에 넣는다. callable 두 개를 순서대로 호출하는 방식은 금지한다.
- 기존 `exchangeClassroomCurrency`를 증권 입출금으로 우회 호출하지 않는다. 포인트↔DJ코인 환전은 원래 기능대로 유지한다.
- 로그인 변경·성공한 입출금 이후 계좌와 지갑 캐시를 함께 무효화한다. 다른 계정의 늦게 도착한 응답을 버린다.
- 오류 응답에는 안정된 code, 학생용 설명, 재시도 가능 여부를 제공한다. 권한 오류에 다른 학생의 잔액이나 존재 여부를 노출하지 않는다.

## 9. 예상 파일 구성과 수정 범위

신규 파일명은 제안이며 기존 모듈 규칙에 맞춰 조정할 수 있다. 폴더 구조 변경 자체를 목적으로 대규모 리팩터링하지 않는다.

기존 파일은 `public/index.html`, 교실 form/workspace/usecases/state 등 실제 연결부, `functions/index.js`, 번들 빌드 목록, 필요한 테스트·npm script만 최소 수정한다. 프런트 domain은 표시/미리보기용이며 서버 계산을 권위로 삼는다. 산식 중복이 있으면 같은 fixture 기대값으로 일치 검증한다.

`firestore.rules`와 `firestore.indexes.json`은 승인 후 필요한 범위만 변경한다. 인덱스는 실제 query에서 필요한 것만 추가한다. `rankingRecords`·`userRankingSummary`·`quizKingSummary`에는 증권 기록을 저장하지 않는다. 레거시 Apps Script 파일과 `../economy`는 이 작업 범위가 아니다.

## 12. 승인·배포·중단 계획

저장소 `AGENTS.md`의 “보안 규칙이나 학생 데이터에 영향을 주는 변경은 영향과 검증 방법을 먼저 설명하고 사용자 확인 후 진행한다” 및 “요청 없는 firebase deploy, git commit, git push를 하지 않는다”를 따른다. **이 문서 작성 요청만으로 해당 조치가 승인된 것은 아니다.**

| 게이트 | 미리 완성할 것 | 확인받을 내용 |
| --- | --- | --- |
| G1. 학생 데이터·규칙 영향 구현 전 | 로컬 UI·순수 계산·합성 fixture·구체적 스키마/API/권한 설계 | 신규 학생 저장 경로, 권한, DJ코인 영향과 Emulator 검증 범위 |
| G2. 실제 재화 운영 연결 전 | Emulator 완성본, 보존식·동시성 검사, 20/60/120일 공급량 보고 | 실제 모드 정책·한도·순유출 경고 기준·시범 학급 |
| G3. 원격 공개 전 | 전체 검사 결과, 현재 배포와 차이, 대상 Functions/규칙/인덱스/Hosting 목록 | 명시된 범위의 배포 및 초기 시장 생성 |

후속 대화에서 이미 구체적으로 승인된 범위는 다시 요청하지 않는다. 승인 대기 중에는 영향을 받지 않는 로컬 작업·문서·테스트 준비를 계속한다.

배포는 인덱스/규칙 준비 → 신규 Functions(기능 비활성) → Hosting → 승인된 시장 초기화 → 교사 시범 → 학생 공개 순서를 제안한다. 기존 미커밋 변경이 함께 섞인 파일은 전체 배포로 무심코 공개하지 말고, 변경 출처와 포함 범위를 먼저 대조한다.

중단 시 신규 입금·매수를 막고 조회·정상 청산·출금 경로를 유지한다. UI만 롤백해 계좌 자산에 접근할 수 없게 만들지 않는다. 이미 생성한 원장·학생 계좌를 삭제하거나 과거 코드로 잔액을 덮어쓰지 않는다. 서버 schemaVersion 호환과 데이터 보존을 우선하고, 복구가 필요하면 차이 보고서·수정 계획을 별도 승인받는다.

## 13. 후속 확장 원칙

- **배당:** 기준일 보유량 snapshot, 계좌별 지급 멱등 키, 재시도 cursor, 지급 예산과 DJ코인 공급 영향이 정해진 후 추가한다. 조회할 때 지급하지 않는다.
- **시총 지도:** 실제 저장한 발행주식수 × 공개 주가를 사용한다. 주가가 높은 기업이 큰 기업이라는 오해를 줄인다.
- **성과 비교:** 실현·미실현·비용·입출금 시점을 반영하는 성과 산식을 먼저 결정한다. 보유분 수익률을 전체 투자 순위로 쓰지 않는다. 외부 퀴즈 랭킹과 분리한다.
- **공동체 기업:** 학생 활동 점수와 주가를 연결하기 전에 중복 반영·편중·부정 제출·낙인·개인정보 공개 문제를 별도 설계한다. 참여 인원 차이를 정규화하고 실명 성과 공개를 기본으로 삼지 않는다.
- **시즌 종료:** 자동 자산 삭제나 전액 강제 매도를 하지 않는다. 종료 시점 평가·학생 안내·청산·소수 잔액·이월 정책을 별도 승인받는다.

- 미수행: 기능 구현, 규칙·설정 변경, 학생 계좌 생성/변경, 운영 데이터 조회를 통한 경제 통계 산출, 배포·커밋·푸시.
- 본 문서의 산식·공수·기본값은 구현 제안이며 자동 검사 통과나 운영 승인 사실을 뜻하지 않는다.
