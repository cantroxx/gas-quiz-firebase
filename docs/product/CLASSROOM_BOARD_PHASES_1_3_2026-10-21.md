# 전자칠판 수업 보드와 그라운드 이전 준비 — 1~3차 실행 목표

작성일: 2026-10-21

사용자 요청: 참고 이미지의 활동 목록·학생 카드·완료 표시를 DJ48 4-8 교실에 맞게 구현한다. 이 문서를 기준으로 1~3차 로컬 구현·검증을 끝내고 보고한다. 후작업은 [별도 문서](../operations/CLASSROOM_BOARD_FOLLOWUPS_2026-10-21.md)에 기록한다.

## 범위와 판정

- 하트베리 → DJ코인, 포인트 → 교실 포인트. 기존 금액을 임의 환산하거나 반올림하지 않는다.
- 기존 퀘스트·제출·젬·교실 지갑을 연결한다. 새로운 화면이 기존 보상과 중복 지급하지 않게 한다.
- 운영 배포, 실제 학생 데이터 이전·지급·회수, 보안 규칙 배포는 별도 실행 범위다. 이 문서의 완료는 로컬 구현과 검증 완료를 뜻한다.
- 실제 데이터의 학생 대응 관계와 원본 내보내기는 아직 확정되지 않았다. 합성 자료로 이전 준비 기능을 검증하며 실명·잔액 원본을 문서에 복사하지 않는다.
- 각 항목은 구현 파일·검증 결과가 확보된 뒤 완료로 바꾼다. 계획 문서 작성 자체를 기능 완료로 계산하지 않는다.

## 확인한 출발점

2026-10-21 대화 중 운영 UI 재검증 및 로컬 소스 확인을 기준으로 한다. 운영과 로컬 전체 파일이 동일하다는 검증은 하지 않았다.

- DJ48 관리자 계정에서 교실·퀘스트·루틴·직업·젬·은행·증권 조회가 가능했다.
- DJ48 학생 카드는 22명, 그라운드에는 학생 21명과 교사 카드가 보였다. 교사 및 추가 학생을 숫자나 닉네임만으로 자동 매칭하지 않는다.
- 신규 퀘스트의 젬 선택은 비어 있고 기존 퀘스트 수정에서는 목록이 나왔다. 목록 초기 로딩 경로를 보완한다.
- 젬 학생 표는 소스에서 20명으로 잘려 있다. 같은 이름의 젬도 있어 ID 기준으로 구분해야 한다.
- 은행과 미션의 학급 포인트 합계는 대상·반올림 기준이 다르다. 기존 개인 포인트 조정은 정수 입력이므로 소수 잔액 이전 경로로 쓰지 않는다.
- 참고 이미지는 좌측 활동 목록, 우측 학생별 카드, 카드/리스트 전환, 완료 상태, 적용 인원과 기간을 보여준다. 이를 기능 요구로 참고하며 이미지 속 학생 정보·아바타를 복제하지 않는다.

## 1차 — 기본 수업 보드

목표: 교사가 전자칠판에서 활동별 학급 전체 상태를 확인하고 학생의 완료를 처리한다.

| 번호 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 진입·전체화면 | 교실에서 수업 보드 진입, 전체화면 진입/해제, 활동 목록 접기, 기존 화면 복귀 |
| 2 | 왼쪽 활동 목록 | 오늘/이번 주/전체, 검색, 분류·기간 상태와 완료/대상 인원·보상 표시 |
| 3 | 학생 카드·리스트 | 번호·닉네임·기존 아바타·상태, 번호순 정렬, 카드/리스트 전환 |
| 4 | 학급 전체 배치 | 교사 제외, 전원 접근 가능, 넓은 화면 밀도 조절, 긴 이름 줄바꿈 |
| 5 | 상태 표현 | 미완료·제출/검토 대기·완료와 보상 지급 여부 구분, 색상 외 텍스트·아이콘 |
| 6 | 교사 개별 완료 | 학생 제출 없이 교사가 완료 가능, 권한·학급·대상·회차 검증 |
| 9 | 수업 중 갱신 | 자동 갱신, 수동 새로고침, 마지막 갱신·연결 실패 표시, 진행 중 중복 요청 방지 |
| 11 | 공개 보기·조작 잠금 | 기본 공개 보기에서 잔액·비공개 제출 숨김, 교사 조작 전환과 재잠금 |
| 12 | 터치·가독성 | 큰 터치 버튼, 키보드 접근, hover 불필요, 좁은 화면 대응 |
| 13 | 기존 승인 통합 | 기존 제출 승인과 보드 완료가 같은 지급 기록을 사용, 동시/재시도 지급 1회 |
| 14 | 반복 활동 회차 | 한 번/매일/매주를 한국 시간 기준으로 분리, 과거 회차 조회·현재 회차와 구별 |
| 16 | 신규 젬 선택 오류 | 신규 등록 경로에서도 젬 목록 로드, 빈 목록과 로딩/실패 구분 |

검증: 합성 학급의 0명·22명·23명, 긴 닉네임, 대상 일부 지정, 만료/미시작 활동, 날짜·주 경계, 학생/타학급 권한, 중복 처리, 좁은 화면과 1920×1080 화면을 점검한다.

## 2차 — 실제 수업 운영 완성

목표: 제출물 확인, 일괄 처리, 실수 취소를 일관된 기록으로 제공한다.

| 번호 | 작업 | 완료 기준 |
| --- | --- | --- |
| 7 | 일괄 처리 | 선택/전체 선택/해제, 대상 수·예상 보상 확인, 성공·실패별 결과, 안전한 재시도 |
| 8 | 완료 취소 | 사유 기록, 실제 지급 포인트와 해당 젬 기여분 회수, 중복 취소 방지, 잔액 부족·후속 보상 충돌 시 부분 회수하지 않고 이유 표시 |
| 10 | 제출 내용 확인 | 교사 상세에서 제출·피드백 확인, 공개 보기에 자동 노출하지 않음 |
| 15 | 제출 유형 | 완료형·상중하·체크리스트·글·이미지의 저장/표시/검증, 기존 퀘스트 하위 호환 |

검증: 개별/일괄 중복, 승인 직후 취소, 재완료, 이미 사용한 보상, 다른 활동이 올린 젬, 재접속, 잘못된 제출 내용·이미지 주소, 권한 없는 조회/수정. 이미지 업로드가 별도 권한 변경을 요구하면 사용 가능한 기존 업로드 경로와 제약을 명시한다.

## 3차 — 이전 준비와 과거 기록 연결

목표: 그라운드 기록을 어떤 학생·활동·젬에 연결할지 검증하고, 과거 완료가 새 보상을 만들지 않게 한다.

| 번호 | 작업 | 완료 기준 |
| --- | --- | --- |
| 17 | 전원 표시·ID 구분 | 젬의 20명 제한 제거, 같은 이름도 ID로 구분, 상품 누락 가격은 임의 채우지 않고 식별 가능한 검증 결과 제공 |
| 18 | 학생·재화·합계 통일 | 교사 제외 기준 공유, 미매칭 학생을 명시, 포인트 소수 보존, 은행/미션이 같은 학급 대상·합계 기준 사용 |
| 19 | 과거 기록 표시 | 원본 ID·회차·이전 출처 표시, 일반 신규 완료와 구별, 과거 기록 열람이 지급·젬 진행을 재실행하지 않음 |
| 3차 공통 | 이전 사전 검증 | 학생/활동/젬 매핑, 재화 매핑, 중복·미매칭·지원 불가 항목 보고, 합성 입력으로 재실행 안정성 검증 |

실제 이전 전에 필요한 원본: 학생 고유 ID, 활동·회차·상태, 지급 여부/내역, 젬 고유 ID·진도, 지갑 잔액과 기준 시각. 없는 정보를 추정해 채우지 않는다. 이미 이관한 기록을 다시 지급하는 일반 완료 API로 넣지 않는다.

3차 완료가 그라운드의 모든 기능을 대체했다는 뜻은 아니다. 다중 직업, 급여 세금, DJ코인 예금, 일일 루틴 등은 후작업 문서의 이전 차단 항목으로 유지한다.

## 구현 순서와 검사

1. 현재 기존 변경을 보존하고 관련 모듈·테스트 경계를 확인한다.
2. 보드 상태/회차/집계·이전 검증 로직, 서버 권한·처리 일관성부터 구현한다.
3. 1차 UI와 기존 경로를 연결하고 2차 제출/일괄/취소를 연결한다.
4. 3차 매핑·과거 기록·합계와 기존 젬 표시를 정리한다.
5. 의미 있는 도메인·서버 테스트, 브라우저 화면 검증, `npm run check:static` 및 `npm run check`를 수행한다. 실패가 기존 문제인지 이번 변경인지 구분한다.
6. 아래 완료 기록을 갱신하고, 전체 점검에서 나온 추가 항목을 후작업 문서에 기록한 뒤 사용자에게 보고한다.

### 수업 사용 흐름

1. 교사 교실 화면 → **전자칠판 수업 보드**.
2. 날짜와 활동을 선택한다. 기본 공개 보기에는 완료 상태만 나타나며 학생 잔액·제출 본문을 넣지 않는다.
3. **교사 조작 열기**에서 이 창에서 사용할 암호를 설정한다. 잠근 뒤 다시 열 때 같은 암호를 쓰며, 5분간 조작이 없으면 잠긴다. 이 암호는 우발적인 화면 터치를 막는 장치이며 실제 권한은 서버의 학급 관리자 검증이 담당한다.
4. 개별 완료 또는 학생 선택 → 완료·승인 → 인원·예상 포인트 확인 → 처리. 이미 처리한 학생과 실패한 학생은 결과에 구분한다.
5. **상세 보기**에서 제출물·피드백·과거 기록을 확인한다. 이미지 표시에는 별도 버튼을 둔다. 완료 취소는 사유를 받고 지갑·젬을 한 트랜잭션으로 회수한다.
6. 목록과 상태는 15초 주기로 자동 조회한다. 연결 실패와 마지막 갱신 시각을 표시하며 새로고침도 가능하다.

학생의 기존 퀘스트 버튼은 새 제출 창으로 이어진다. 이미 제출한 활동에는 **내 제출·피드백 보기**를 제공한다. 이미지 제출은 브라우저에서 긴 변 720px 이하, 데이터 URL 180,000자 이하로 축소해 교사/본인 전용 제출 컬렉션에 보관한다. 원본 고해상도 파일 보존 기능은 아니다.

### 완료·취소·이전의 경계

- 학생 자동 완료, 교사 직접 완료, 기존 검토 승인이 공통 서버 처리를 사용한다. 회차·학생별 원장과 요청 ID가 중복 지급을 방지한다.
- 실제 지급한 소수 포인트, 부스터 가산, 해당 완료가 만든 젬 진행·젬 달성 포인트·DJ코인을 함께 기록한다.
- 취소 시 잔액이 부족하거나 후속 젬 변경이 있으면 전체 취소를 거부한다. 일부만 회수하거나 음수 잔액을 만들지 않는다.
- 구버전 지급처럼 회수 근거 원장이 없는 기록은 자동 취소하지 않고 이유를 표시한다. 안전한 레거시 원장 대조는 후작업으로 명시한다.
- 그라운드 과거 기록은 `boardHistory`에 원본 ID·날짜·지급 여부를 보관한다. 동일 ID·동일 내용은 중복 보관하지 않으며 다른 내용의 덮어쓰기를 거부한다. 열람·보관으로 지갑이나 젬을 바꾸지 않는다.
- 이미 이전한 완료 회차를 일반 완료/승인으로 다시 지급하지 않는다. 왼쪽 활동 완료 인원과 학생 카드 모두 이전 완료를 포함한다.
- 교사와 숨김 학생을 학급 경제 합계에서 제외하고, 은행은 서버 미션 합계와 같은 포인트 값을 사용한다. 교사가 숨김 학생을 조회하는 기존 기능은 유지한다.
- 실제 지갑 잔액을 쓰는 마이그레이션은 실행하지 않았으며 이번의 미리보기 도구는 지갑을 쓰지 않는다.

### 사전 검증 입력과 실행

```sh
node scripts/migration/preview-grownd-classroom.js \
  fixtures/classroom-board/grownd-example.json \
  fixtures/classroom-board/target-example.json
```

예제 결과: `ready: true`, 포인트 합계 `215.75`, DJ코인 합계 `122.5`, 과거 기록 1건. 합성 자료이며 실제 학급 잔액이 아니다.

- `version: 1`, `source: "grownd"`, `asOf`: 기준 날짜.
- `students`: 원본 ID, 원본 `point`, `heartberry`. 교사 원본은 `role: "teacher"`로 구분한다.
- `maps.students`, `maps.quests`, `maps.gems`: 원본 ID → 대상 ID의 명시적 대응표.
- `records`: 원본 기록 ID, 원본 학생/활동 ID, 날짜, `completed/pending/incomplete`, 원본 지급 여부, 원본 젬 ID 배열.
- `excludedTargetStudents`: 원본이 없는 대상 학생을 이번 이전에서 제외하기로 결정한 경우에만 `{memberUserId, reason}`으로 명시한다. 매핑과 동시 제외는 오류다.
- `unsupported`: 아직 이전하지 못하는 데이터 종류. 비어 있지 않으면 준비 완료로 판정하지 않는다.
- 실제 원본·대응표는 공개 Git에 넣지 않는다. 이 도구는 원본을 읽고 결과를 출력하며 자동 저장·업로드하지 않는다.

보드의 **이전 자료 사전 검증**도 같은 규칙을 사용한다. 과거 기록 보관 서버 경로는 `classroomBoardAction / importHistory`이며 한 번에 100건 이하, 교사 권한, 사전 검증 통과를 요구한다. 화면에는 실행 버튼을 두지 않았다. 실제 호출은 원본 대조와 사용자 이전 요청 이후의 운영 작업이다.

## 운영 반영 전 인계

이번 작업에서 배포·운영 학생 데이터 이전·커밋·푸시는 하지 않았다. 기존 작업 트리의 다른 변경을 되돌리지 않았다.

배포를 요청받으면 현재 운영본과 작업 트리 차이를 먼저 분리한다. 프런트와 `classroomBoardAction`, `completeClassroomAutoQuest`, `reviewClassroomQuestProgress`, `saveClassroomQuest`, `getClassroomEconomyBoard`, `getClassroomStudentCards`의 호환성을 함께 검토해야 한다. 새 프런트만 단독 배포하면 새 서버 경로를 호출할 수 없다. 이번 작업으로 보안 규칙·인덱스 파일을 수정하지 않았다.
