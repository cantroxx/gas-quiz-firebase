## 분석 범위와 확인 방법

운영 아지트 스크립트가 로컬과 일치함을 확인했고, 운영 앱 번들은 랭킹 부분이 동일했다. 운영 Firestore 규칙도 읽기 전용 조회로 확인했다. 학생 프로필을 수집하지 않고 실제 렌더러·로더와 합성 50명으로 읽기 호출 수 및 카드 생성 시간을 측정했다. 도구: `node scripts/audit/ranking-loading-profile.js`.

아래 수치는 SDK `.get()` 호출 수다. HTTP 연결 수나 청구되는 문서 읽기 수와 동일하다고 해석하면 안 된다. 렌더 시간은 DOM 카드 생성만 측정하며 이미지 다운로드·레이아웃·기기 성능은 포함하지 않는다. 실제 학교 네트워크에서의 초 단위 응답 시간은 측정하지 않았다.

## 확인된 병목

1. **전체 퀴즈 조회가 끝나야 탭을 만든다.** `showRankingView` → `renderRankingView`는 기존 보드를 지우고 로딩 문구를 표시한다. `loadRankingPlazaData`는 시즌 설정, 모든 분야의 순위/시즌 기록, 회원 프로필까지 기다린 뒤 보드 모델을 돌려준다. 아지트 탭 주입도 그 뒤에 가능하다. 한 분야가 느리면 아지트 진입까지 함께 늦어진다.
2. **선택 전 조회량이 크다.** 분야 설정은 36개 항목, 고유 35개다. `인기이모지-티니핑`이 중복돼 같은 쿼리를 두 번 실행한다. 비활성 분야 필터 적용 전 설정상 반환 상한은 합계 7,116문서다(일반 41, 포켓몬 241, 티니핑 801; 공개 제외 회원 보충 1 포함). 실제 반환 수를 측정한 값은 아니다. 여기에 시즌별 200개 단위 전체 페이지 조회와 회원 최대 180명의 기본 프로필 720회 조회가 추가된다.
3. **프로필 결합이 사람별 개별 조회다.** 각 사람마다 `users`, `userTitleSummary`, `userLevelSummary`, `userRoomSettings` 네 문서를 읽는다. 서바이버·구름탑은 그 전에 `presence`도 읽는다. 칭호 이름이 비어 있으면 `userTitles`와 `titleCatalog`, 이미지 URL이 없으면 Storage URL 조회 단계도 뒤따른다. 아지트 개편에서 공통 프로필 표시를 붙이면서 생긴 추가 비용이다.
4. **다른 학생의 비공개 필드도 읽으려 한다.** 운영 규칙에서 `userTitleSummary`, `userRoomSettings`, `userTitles`는 본인 연결 계정만 읽을 수 있다. 일반 학생으로 친구 랭킹을 볼 때 이 요청들은 실패하며 `.catch(() => null)`로 숨겨진다. 50명이 모두 다른 학생인 경우 기본 200회 중 100회는 사용할 수 없는 조회다. 이는 프로필을 읽기 위해 규칙을 공개로 바꾸어야 한다는 뜻이 아니다.
5. **재진입 때 캐시를 재사용하지 않는다.** `ranking-visibility.js`는 패널이 보일 때마다 load를 호출한다. 아지트 로더는 중복 진행 요청만 막고 이미 받은 rows나 갱신 시간으로 건너뛰지 않는다. 캐시가 있어도 ‘기록을 불러오는 중’으로 지우고 목록·프로필을 다시 기다린다. 서로 다른 분야가 같은 학생을 표시해도 프로필 조회를 공유하지 않는다.
6. **추가 지연 가능성.** 스터디 타운 list는 서버에서 난이도별 전체 기록을 조회·정렬한 후 반환하고 클라이언트가 50개를 자른다. 퀴즈 보드 렌더도 숨긴 하위 분야까지 한꺼번에 만든다. Functions 콜드 스타트나 실제 모바일 렌더 지연의 기여도는 이번 측정으로 확정하지 않았다.

## 분석 당시 개선 우선순위

1. 보드 탭을 즉시 표시하고 선택한 분야의 기록부터 조회·렌더한다. 한 분야 오류가 다른 분야 표시를 막지 않게 한다.
2. 짧은 유효기간의 목록/프로필 캐시를 공유하고 재진입 때 먼저 기존 카드를 표시한다. 새로고침·기록 저장·프로필 변경·로그아웃 시 무효화한다.
3. 본인만 읽을 수 있는 문서 조회를 친구 프로필 경로에서 제거한다. 공개 표시 필드는 이미 허용된 프로필 값이나 검증된 공개 표시 전용 응답으로 결합한다. 규칙 완화로 해결하지 않는다.
4. 중복 분야 쿼리를 없애고 상위 표시 대상만 프로필을 보강한다. 시즌 기록은 무작정 잘라 순위를 누락시키지 않고 정확한 집계 구조를 먼저 검토한다.

위 초기 배포는 링크 삭제만 포함했다. 이후 사용자의 ‘진행’ 지시에 따라 아래 성능 개선을 구현했다.

## 승인 후 성능 개선

- `ranking-plaza-loader.js`가 기록을 기다리지 않고 분야 탭을 먼저 표시한다. 선택한 분야와 보이는 ‘오늘의 왕’만 조회하고, 명예의 전당 전체는 펼칠 때 조회한다. 시즌 설정 및 해당 기간 기록은 시즌 탭 선택 시 불러온다. 시즌 순위 계산과 페이지 조회의 정확도는 유지했다.
- 일반 랭킹 분야별 목록, 아지트 게임·난이도별 목록을 60초 캐시한다. 숨긴 일반 분야 패널도 선택 시 렌더한다. 갱신 중·실패 시 이전 순위를 유지하며 명시적 새로고침 버튼으로 다시 조회할 수 있다.
- 프로필 및 UID→회원 연결 문서는 Firestore 인스턴스·인증 UID·회원 ID별 60초 캐시를 공유한다. 동시에 요청한 동일 문서는 한 번만 읽고 실패한 요청은 캐시하지 않는다.
- 친구 프로필의 `userTitleSummary`, `userRoomSettings`, `userTitles` 읽기를 제거했다. 본인의 설정과 공개 users/level/titleCatalog 경로는 유지했다. 규칙 변경은 없다.
- 중복 분야 키를 제거했다. 프로필 저장·퀴즈 랭킹 저장·전체 새로고침·로그아웃 시 캐시를 무효화한다. 계정·월·기능 설정 변경도 재진입 시 새 범위로 분리한다. 이전 계정/난이도의 늦은 응답은 버린다.
- 퀴즈왕 요약 문서가 없는 경우에만 기존 전체 기록 합산 대체 경로를 유지한다. 정상 요약 경로에서는 전체 분야 조회가 없다.

동일한 합성 50명, 마블 → 서바이버 → 마블 순서에서 측정한 SDK `.get()` 호출 수:

| 시나리오 | 개선 전 | 개선 후 | 변경 |
| --- | ---: | ---: | --- |
| 마블 첫 진입 | 201 | 101 | 친구 비공개 문서 조회 제거 |
| 같은 친구들의 서바이버 전환 | 251 | 51 | 프로필 재사용, 연결 정보만 추가 조회 |
| 1분 내 마블 재진입 | 201 | 0 | 목록 캐시 재사용 |

개선 후 DOM 카드 생성은 약 0.9~1.4ms였다. 실제 학생 수/데이터와 학교 네트워크의 초 단위 체감 속도를 측정한 값은 아니다. 처음 여는 UID 기반 게임은 공유 프로필 캐시가 없으면 목록 1 + 연결 50 + 공개 프로필 100으로 최대 기본 151회가 필요하다. 칭호/Storage 보강은 별도이며, 스터디 타운 서버 측 정렬·콜드 스타트는 이번 변경 범위에 포함하지 않았다.

검증: 독립 포트 복사본 `/tmp/hideout-check`에서 전체 `npm run check` 통과. 저장소·유스케이스 검사에 권한별 읽기, 병렬 중복 제거, TTL, 실패 재시도, 분야·시즌별 조회 분리 검사를 추가했다. `hideout-ranking-browser.js`와 `ranking-plaza-loading-browser.js`는 최신 운영본을 보존한 실제 배포 후보 번들에서도 통과했다. 새로고침 시 기존 행 보존, 오류 복구, 계정 전환 중 늦은 응답, 난이도 캐시, 모바일 표시를 포함한다.

성능 개선 배포: Hosting 버전 `65419bd99c258f76`, release `1789543593727000`. 최신 운영 버전 `3582b1a7feb62673`을 복제해 랭킹 관련 7개 파일만 교체했다. 나머지 파일 392개, 번들의 다른 모듈과 Hosting 설정은 동일함을 확인했다. 기존 퀴즈 서바이버 초기화는 반복하지 않았다. 학생 데이터·Functions·보안 규칙 배포는 없다.

배포 후 7개 운영 파일의 SHA-256이 검증 후보와 모두 일치했고 운영 공개 로그인 화면 브라우저 검사도 통과했다.
