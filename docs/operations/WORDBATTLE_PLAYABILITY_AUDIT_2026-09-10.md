# 낱말 루미큐브 온라인 지연·재미 개선 점검

점검일: 2026-09-10. 소스 분석과 실제 클라이언트 코드를 이용한 합성 테스트. 운영 방 생성·학생 기록 변경·배포 없음.

## 결론과 범위

학교 와이파이만의 문제로 판단할 근거는 없다. 현재 구현에는 네트워크 지연을 키우는 통신 순서와 중복 요청, 갱신 방식이 있다. 학교에서 발생한 지연의 주원인은 아직 확정하지 못했다. 실제 2~4인 대전의 네트워크·서버 처리 시간은 이번에 측정하지 않았다.

이전 공개 첫 화면 정상 판정은 온라인 한 판 전체의 응답성을 보장하지 않는다.

## 확인한 항목

| 우선순위 | 코드 근거 | 확인 결과와 의미 |
| --- | --- | --- |
| 높음 | `public/wordbattle/net.js` runAction | 방 읽기 후 손패 읽기, 이후 커밋을 기다린다. 힌트·동의 등도 방 전체와 손패를 쓴다. 합성 전송 단계 100ms에서 304ms, 300ms에서 904ms 소요. 실제 서버 지연 수치가 아니라 현재 순서가 지연을 누적하는지 검증한 값이다. |

| 중간 | `functions/index.js` wbDraw, `main.js` warmUpDrawServer | 뽑기·시간초과만 서울 리전 서버 함수를 거친다. 페이지 진입 시 ping은 있지만 운영 cold start 시간은 미측정. cold start를 주원인으로 단정하거나 상시 인스턴스 비용을 먼저 추가하지 않는다. |

Firestore 웹 트랜잭션의 충돌 시 재시도 가능성은 [공식 문서](https://firebase.google.com/docs/firestore/transaction-data-contention)와도 일치한다. Functions 초기 실행 지연은 [공식 성능 안내](https://firebase.google.com/docs/functions/tips)를 참고하되 운영 측정 후 판단한다.

## 게임 완성도 관련 별도 발견

- 현재 턴 제한은 2분이다. 4인에서 다른 세 명이 시간을 모두 쓰면 내 차례까지 약 6분을 기다릴 수 있다. 통신 지연과 별개인 규칙상 대기 시간이다.
- 결과 저장 중복 방지는 화면 메모리의 recorded 변수뿐이다. 네트워크 계층의 recordRank는 매번 점수·게임 수를 증가시킨다. 같은 결과를 다시 기록하지 않도록 경기 ID를 기준으로 한 중복 방지가 필요하다. 실제 중복 적립 발생 여부는 운영 기록을 조사하지 않았다.
- 방·봉지·손패 쓰기 규칙이 참가자/호스트/허용 변경 필드로 충분히 제한되지 않고 인증 여부에 크게 의존한다. 점수도 클라이언트가 계산·저장한다. 경쟁 랭킹을 확장하기 전에 공정성 보완 대상으로 삼는다. 현재 악용됐다는 뜻은 아니다.
- 실패한 랭크 저장은 화면 메시지가 비워지고 자동 재시도가 없다. 연결이 불안정한 환경에서 승리 결과 보존 경험을 보완해야 한다.

## 권장 진행 순서

1. 합성 방/손패로 2~4인·느린 응답·수신 순서 교차·연결 끊김을 재현한다. 실제 학생 계정과 운영 랭킹은 사용하지 않는다.
2. 타임아웃 단일 진행 요청, 턴 식별을 통한 오래된 요청 처리, 불필요한 손패 쓰기 감소, 구독 오류 안내, 편집판 보존을 보완한다. 서버 확정 전에 성공한 것처럼 보상을 지급하지 않는다.
3. 조작→화면 반응, 확정→서버 응답, 확정→상대 화면 반영 시간을 따로 측정한다. 학생 이름·손패·인증정보 대신 익명 합성 식별자와 소요 시간만 기록한다.
4. 동일 기기·동일 게임 조건으로 학교 와이파이와 다른 네트워크를 비교한다. 타일 이동/낱말 확정/뽑기를 각각 반복하여 중앙값·느린 상위 5%·실패율을 비교한다. 다른 네트워크에서도 동일하면 게임 쪽, 학교에서만 악화하면 네트워크 영향이 강하다는 판단 근거로 삼되 단일 원인으로 단정하지 않는다.
5. 재미 실험: 연습방에서 45/60/90/120초 턴 선택, 상대 턴의 개인 낱말 연습장, 되돌리기·자모 정렬, 최근 완성 낱말 강조를 비교한다. 상대 턴 연습장은 실제 손패/공용판과 분리하고 실제 차례에 다시 검증한다.
6. 학생 플레이에서 대기 때문에 이탈하는지, 규칙을 이해하는지, 다시 한 판 하고 싶은지를 확인한다. 제한 시간을 줄여 생각할 시간이 부족해지지 않는지도 함께 본다.
7. 점수 저장·방 권한 강화는 영향과 합성 권한 테스트를 준비한 뒤 사용자 확인을 받아 진행한다. 배포와 유료 상시 서버 설정은 별도 실행 단계다.

## 승인과 보존

이번에는 게임 소스를 수정하지 않았다. 이 문서만 추가했다. 운영 개인정보·회원·학생 데이터 조회/수정/삭제, 방 생성, 랭킹 등록, Rules 변경, commit/push/deploy는 하지 않았다.

사용자에게 필요한 현장 정보는 렉이 주로 발생하는 동작(타일 이동/확인/뽑기/상대 차례 전환), 대략적인 지연 시간, 사용 기기와 인원이다. 이 정보가 없어도 위 합성 재현과 로컬 보완 설계는 진행할 수 있다.

## 후속: 두 브라우저 화면 재현 결과

사용자의 추가 점검 요청에 따라 `scripts/audit/wordbattle-online-diagnostic.js`를 추가했다. `node scripts/audit/wordbattle-online-diagnostic.js`로 실행한다. Chrome과 기존 playwright-core가 필요하다.

실제 `ui.js`, `net.js`, 낱말 판정·게임 규칙 및 CSS를 두 독립 브라우저 컨텍스트에 로드했다. 뽑기는 `functions/index.js`의 실제 wbDraw 콜백을 추출해 메모리 DB 어댑터로 실행했다. 브라우저의 외부 요청은 모두 차단했다. Firebase SDK/실제 Firestore 전송, 충돌 재시도, 콜드 스타트, 학교 회선은 이 테스트에 포함되지 않는다.

| 인위적으로 넣은 통신 단계별 지연 | 낱말 확인 클릭→상대 차례·낱말 반영 | 뽑기 클릭→상대 차례 반영 |
| --- | --- | --- |
| 0ms | 57ms | 45ms |
| 100ms | 463ms | 252ms |
| 300ms | 1,254ms | 660ms |

각 조건은 최종 실행의 단일 측정값이며 중앙값이나 p95가 아니다. 일반 클릭 처리 비용도 포함한다. 낱말 확정은 방 읽기→손패 읽기→커밋→상대 수신까지 합성 지연이 누적된다. 뽑기는 테스트 서버 내부 DB 지연을 넣지 않았으므로 운영에서 뽑기가 더 빠르다는 결론은 낼 수 없다. 세 조건 모두 실제 낱말 `가나`가 반영되고, A의 손패 1장/B의 손패 6장 및 A로의 차례 복귀를 확인했다.

추가 재현:

1. **늦은 손패 수신 시 편집 초기화**: 기존 손패를 편집할 수 있는 상태에서 새로운 손패를 1초 늦게 전달했다. 만드는 중 칸에 놓은 타일이 1개에서 0개가 됐다. 손패 자체가 삭제된 것은 아니고 편집 상태가 초기화된 것이다. 이는 의도적으로 만든 불리한 수신 조건에서의 UI 동작 확인이며, 실제 Firestore에서 이 조건이 발생하는 빈도나 정상 시작 시 발생 여부를 입증하지 않는다.
2. **응답 대기 중 타임아웃 중복 요청**: timeout 응답을 해결하지 않은 채 실제 UI 타이머를 10.5초 실행하자 3회 호출했다. 네트워크 장애 시 진행 중 요청을 하나로 제한할 필요가 있다. 실제 서버가 세 번 턴을 넘겼다는 의미는 아니다.

판정: 느린 통신에서 상대 반영 시간이 누적되는 구조, 지연 손패가 편집 상태를 초기화하는 동작, 응답 대기 중 중복 요청은 재현됐다. 학생들이 겪은 렉의 주원인과 학교 회선 영향 비율은 아직 확정할 수 없다. 게임 쪽 보완 우선순위는 진행 중 요청 단일화→수신 상태 일관성/편집 보존→불필요한 통신 감소→연결 상태 안내다.

진단 스크립트 구문 검사와 `git diff --check` 통과. 게임·Functions·Rules 코드는 변경하지 않았고 테스트 코드 및 이 보고서만 추가·갱신했다. 운영 데이터나 배포 변경은 없다.

## 후속: 사용자 요청에 따른 로컬 수정 완료

위 내용은 수정 전 진단 이력이다. 이후 사용자의 “작업 후 보고” 요청으로 다음을 로컬에 반영했다. 운영 배포는 아직 하지 않았다.

- `net.js`: 방과 손패 읽기를 병렬 실행한다. 손패가 바뀌지 않는 힌트·동의 등의 액션에서는 손패를 다시 쓰지 않는다. 같은 이벤트 루프의 구독 알림은 묶고, 진행 중인 온라인 액션의 중복 실행을 차단한다.
- `net.js`/`ui.js`: 방의 본인 손패 개수와 수신된 손패 개수가 맞지 않으면 조작을 잠시 잠근다. 같은 차례·공용판에서 손패만 추가되면 조합 중인 타일을 보존한다. 실제 차례나 공용판이 바뀌면 서버 상태를 따른다. 같은 개수의 서로 다른 손패 버전을 완전히 판별하는 버전 프로토콜까지 도입한 것은 아니다.
- `ui.js`: 시간초과 요청은 응답 대기 중 하나만 유지한다. 성공 후에는 같은 차례의 요청을 반복하지 않으며, 실패하면 기존 간격으로 재시도할 수 있다. 일시정지 자동 해제 요청도 중복을 막았다. 서버 응답 대기·일시정지 중 타일 편집을 차단한다.
- 연결 끊김, 방·손패 맞추는 중, 구독 오류를 안내한다. 브라우저의 오프라인 신호가 돌아오면 화면을 재확인한다. 이 표시는 모든 회선 품질 저하를 감지하는 속도 측정 기능은 아니다.
- `index.html`의 수정 JS/CSS 캐시 버전을 갱신했다. Functions·보안 규칙·점수 산식·랭킹 저장 정책은 변경하지 않았다.

검증:

| 검사 | 결과 |
| --- | --- |
| 두 브라우저 지연 재현 | 300ms/단계에서 상대 낱말 반영: 수정 전 1,254ms → 수정 후 946~961ms(두 실행). 운영 속도 보장이 아닌 합성 테스트 결과 |
| 응답 없는 타임아웃 10.5초 | 수정 전 3회 → 수정 후 1회 |

| 실제 Firestore Emulator + 현재 Rules | 병렬 트랜잭션 읽기, 두 참가자 낱말·차례 반영, 힌트 후 손패 보존 통과 |
| `npm run check` | 전체 통과. 이 명령의 공개 browser smoke는 기존 운영본을 확인하며, 수정본 온라인 동작 검증은 위 별도 테스트로 수행 |

추가 Emulator 재현 명령:

```sh
firebase emulators:exec --project demo-dj48-rules --only firestore "node tests/rules/wordbattle-online.test.js"
```

다음 실행 단계는 Hosting 배포 후 학교 환경에서 실제 대전 확인이다. 현 단계에서 운영 학생 데이터·회원·랭킹 삭제나 변경은 없고, commit/push/deploy도 하지 않았다. 서버 cold start와 학교 무선망 품질, 4인 동시 충돌/장기 재접속은 아직 현장 검증 대상이다. 전체 화면 재생성 최적화와 재미 규칙 실험은 이번 안정성 수정 이후 보완 대상으로 유지한다.

## 운영 배포 완료

사용자의 “배포진행” 승인으로 2026-09-10 Firebase Hosting 배포를 완료했다. 배포 대상은 `dj48-quiztown-firebase`, 명령은 `firebase deploy --project dj48-quiztown-firebase --only hosting`이다. 새로 업로드한 파일은 4개이며 배포 release 성공을 확인했다.

배포 후 `wordbattle/index.html`, `net.js`, `ui.js`, `style.css`의 운영 응답이 로컬 수정본과 바이트 단위로 일치했다. `SMOKE_PUBLIC_ONLY=1 npm run smoke:browser`도 통과했다. 실제 학생 온라인 대전은 실행하지 않았다.

Functions·Rules·운영 데이터는 배포/수정하지 않았다. Git commit/push는 수행하지 않았으며 수정본과 진단 자료는 현재 작업 트리에 남아 있다. 다음 확인은 새로고침한 두 기기로 학교에서 낱말 확정·뽑기·차례 전환을 비교하는 것이다. 이미 진행 중인 게임은 종료 후 새로고침해 새 버전을 적용한다.
