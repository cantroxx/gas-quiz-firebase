# 퀴즈 정리 후속 단계 실행 계획

작성일: 2026-10-18 KST. 이번 문서는 후속 작업의 순서와 판정 기준을 정리한 것으로, 아래 작업의 실행·배포·삭제 완료 기록이 아니다.

최신 수행 기록: [후속 실행 결과](QUIZ_CLEANUP_FOLLOWUP_RESULTS_2026-10-18.md). 검증은 고정된 퀴즈 변경본 기준이며, 이후 공유 파일의 하우징 변경은 별도다.

## 기준과 현재 상태

- [실행 정본](QUIZ_CLEANUP_EXECUTION_PLAN_2026-10-18.md)의 0~5단계는 로컬 구현·검증 범위에서 완료했다. 시즌 감시 제거, 개인/과목 랭킹 조회 분리, 관리자 검사 범위 제한, 구형 이벤트 집계 호출 제거가 해당한다.
- 운영 반영은 하지 않았다. 운영 읽기·쓰기 감소량과 실제 비용 개선은 아직 측정하지 않았다.
- [검증 증빙](QUIZ_CLEANUP_VERIFICATION_2026-10-18.json)의 전체 검사는 마지막 서버 보완 전 결과다. 이후 관련 에뮬레이터·정적 검사는 통과했다. 후속 실행에서 교실 포인트·주간 한도까지 전후 비교를 완료했고 최종 전체 검사를 다시 통과했다.
- [최초 검토 보고서](QUIZ_CLEANUP_REVIEW_2026-10-18.md)의 함수 줄 번호·파일 수·참조 수는 조사 당시 값이다. 특히 구형 집계 호출 제거 후 미참조 후보 수가 달라질 수 있으므로 다시 조사한다.
- [구형 쓰기 변경 영향](QUIZ_CLEANUP_NEXT_GATE_2026-10-18.md)의 운영 전 조건을 유지한다.

## 6단계 — 기준 재확인과 보상 검증 보완

1. 현재 작업 트리와 기존 baseline/patch/파일 해시를 대조한다. 다른 작업의 수정은 별도 표시한다. 임시 경로의 기준 파일이 사라졌다면 검증 가능한 기준을 복원하기 전 삭제 작업을 시작하지 않는다.
2. 최신 공개 Hosting과 접근 가능한 배포 이력/Functions 소스를 읽기 전용으로 대조한다. 접근할 수 없는 항목은 미확인으로 기록한다. 공개 프런트 일치만으로 서버 일치까지 판정하지 않는다.
3. 합성 데이터에서 구형 집계 호출 제거 전후의 교실 포인트·DJ코인·XP·주간 한도 결과를 독립 비교한다. 트리거 재시도·동시 지급·기능 중지·계정 불일치도 포함한다.
4. 최종 배포 후보에 `npm run check`, `npm run check:subject-online`, `npm run check:cleanup-online`, `npm run check:cleanup-rewards`를 실행하고 파일 해시와 함께 기록한다. 이후 수정한 영역은 다시 검증한다.

산출물: 최신 차이 목록, 미확인 항목 목록, 보상 전후 비교표, 검증 로그. 서버 출처나 보상 차이가 해결되지 않으면 해당 변경의 운영 반영을 보류한다.

## 7단계 — `dailyUsage` 종료 여부 결정

1. `rewardGeneratedSubjectAnswer`, `getPopularQuizUsageStatus`, `recordPopularQuizUsageSeconds`, `recordEducationCorrectForPopularUnlock`, 일반 퀴즈 저장소·관리자 감사를 연결해 읽기/쓰기 지도를 만든다.
2. 현행 인기 퀴즈, 구형 URL·세션·외부 클라이언트가 각각 무엇을 사용하는지 확인한다. 소스 참조가 없거나 짧은 기간 호출이 없다는 이유만으로 소비 종료를 확정하지 않는다.
3. 새 과목 정답 경로의 읽기 1회·쓰기 1회 제거안을 만든다. 구형 API의 호환 응답/종료 안내와 기존 문서 보존은 별도로 명시한다.
4. 학생 데이터 영향과 검증 방법을 제시한 뒤 확인받고 적용한다. 연습·랭킹 정답, 오답, 중복, 보상 한도와 현행 인기 진입 동작을 검증한다.

완료 기준: 소비자별 근거가 있고, 승인된 경로에서 `dailyUsage` 접근 0회이며 보상·접근 정책이 유지된다. 이 단계에서 기존 `dailyUsage` 문서를 삭제하지 않는다.

## 8단계 — 미사용 내부 함수와 종료 UI 정리

1. 최초 보고서의 헬퍼 11개 및 호출 제거 후 `updateEventQuestProgressForKinds` 관련 의존성을 재조사한다. 소스·테스트·스크립트·문자열 호출·export·예약/트리거·빌드 순서를 함께 확인한다.
2. 후보마다 선언, 호출자, 데이터 경로, 외부 노출, 삭제 근거를 표로 만든다. 구형 이벤트 조회 → 표시/문구 → 시즌 관리자 UI처럼 기능별 작은 묶음으로 제거한다.
3. 실제 운영 성장 트리거와 인증 callable은 유지한다. `prepareMonthlySeasonDraft`의 원격 예약 종료는 내부 함수 삭제와 분리해 운영 승인 대상으로 남긴다.
4. HTML 이벤트 연결·DOM·렌더러·상태·저장소 의존성을 함께 확인하고 정상 빌드로 산출물을 갱신한다. 관련 테스트 및 화면 변경 시 전체 검사를 실행한다.

완료 기준: 제거한 각 함수/화면의 미도달 근거, 남은 호환 진입점, 통과 검사가 기록된다. 호출되지 않던 헬퍼 삭제량을 DB 읽기 절감량으로 계산하지 않는다.

## 9단계 — 남은 조회와 이미지 최적화

### 9-A. 반복 조회

- 설정 감시의 숨김 탭 중지·재진입 갱신·진행 중 요청 병합을 검토한다. 현재 완료한 것은 시즌 문서 제외뿐이다.
- 개인/과목 랭킹의 요청 병합·짧은 캐시와 퀴즈왕 전체 집계 최적화 필요성을 실제 호출 경로 기준으로 판단한다. 캐시를 도입한다면 회원·권한 분리, 로그아웃/점수 변경 무효화가 필수다.
- 동점이 많은 과목 조회의 추가 읽기와 501행 상한 오류를 측정한다. 상한을 무작정 늘리거나 숨김/동점 순서를 바꿔 비용을 줄이지 않는다.
- 관리자 문제 점검의 반복 실행 빈도를 확인하고 필요할 때만 캐시를 추가한다. 이전 결과를 새 검사 완료로 오인시키지 않는다.

완료 기준: 합성 시나리오별 호출 수 전후 비교와 변경 감지·계정 전환·동점·부분 실패 회귀 검사를 통과한다. 실측 전 절감률을 운영 비용 개선으로 단정하지 않는다.

### 9-B. 이미지·중복 정적 파일

- 최초 조사에서 인기 이미지 551개는 전부 사용 중이었다. 현재 참조를 다시 계산한 뒤 큰 파일부터 파생본을 시험한다.
- 표시 크기별 식별 품질·출처·원본 해시·파생 경로·용량을 기록하고 모바일/데스크톱에서 확인한다. 얼굴이나 그룹 식별이 어려워지면 해당 이미지는 전환하지 않는다.
- 새 문제의 URL만 파생본으로 전환하고 진행 중 `popularQuizRuns`가 참조하는 기존 URL은 보존한다. 인기 세션은 작성일만으로 만료됐다고 보지 않는다.
- 동일 바이트 파일은 URL·아이템 ID·독립 미리보기 소비자를 먼저 조사한다. 생성 소스와 번들/React 출력은 중복 삭제 대상에서 제외한다.

완료 기준: 누락 이미지 0개, 식별 품질 확인, 실제 시나리오의 전송량 비교, 원본 URL 호환성 보존. 원본 삭제는 11~12단계에서 별도 판단한다.

## 10단계 — 운영 반영과 개선 확인

1. 이번 작업만 포함한 배포 목록·최신 운영 대비 diff·검증 결과·롤백 절차를 준비한다. 로컬 `public/`나 Functions 전체를 무조건 배포하지 않는다.
2. 명시적 배포 승인을 받은 대상만 반영한다. 새 `memberRankings`/`subjectRankings` 액션은 서버를 먼저 반영·검증한 뒤 프런트를 전환한다.
3. 퀘스트 쓰기 중단은 구형 소비자와 보상 검증을 통과한 경우에만 포함한다. 내부 코드 삭제·이미지 전환·스케줄 변경은 승인 범위를 구분한다.
4. 필요한 범위의 호출량·오류·지연·읽기량과 구형 집계 갱신 여부를 관찰한다. 관찰 기간/중단 기준은 반영 전에 정하고, 수업 이용시간을 포함해 판단한다.

완료 기준: 기능 보존 및 비교 가능한 운영 증빙이 확보된다. 기능 오류·보상 차이·구형 소비자 발견 시 해당 변경을 중단/복구하고 데이터 삭제로 넘어가지 않는다. 쓰기 중단 기간의 구형 집계는 소스 롤백만으로 소급 복구되지 않는다.

## 11단계 — 데이터 보존 정책과 삭제 명세

1. 컬렉션 전체 학생 문서 열람 대신 필요한 count·최신 갱신·버전·상태를 제한된 읽기 전용 조사로 확인한다. 조사 쿼리·범위·상한·비용을 먼저 기록한다.
2. 보관 후보는 구형 문제은행, 쓰기가 종료된 `eventQuestProgress`/`dailyUsage`, 종료 시즌 설정, 종료가 입증된 세션 등으로 구분한다. 각 항목에 보존 목적·기간 결정권자·외부 참조를 기록한다.
3. 현역 문제은행과 혼합 랭킹 컬렉션, 출제 deck, 성취 이력은 기본 제외한다. 지급 원장·성장 처리 표식·한도 문서는 재시도/지연 요청/재지급 위험을 해소하기 전 제외한다.
4. 경로·ID·버전·종료 상태·updateTime·참조·하위 컬렉션·제외 사유를 담은 manifest와 dry-run을 준비한다. 자동 만료/TTL 도입도 같은 보존 검토를 거친다.
5. 원본/출처 백업, 접근 통제, 합성 또는 격리 환경 복원 시험, 대사 방법을 준비한다. 기존 `private/`, `exports/`는 임의 조사·정리 대상으로 삼지 않는다.

완료 기준: 사용자가 대상·건수·영향·복원 가능 범위를 확인할 수 있는 삭제 명세가 준비된다. 보존 기간을 임의로 7일/30일로 정하지 않는다. 데이터 삭제와 Rules/인덱스 제거 승인은 별개다.

## 12단계 — 승인된 대상만 정리·검증

1. 승인된 manifest를 다시 대조한다. 버전/최근 수정/참조가 바뀐 문서는 제외한다.
2. 작은 배치로 실행하고 처리·제외·실패 목록을 남긴다. 상위 문서 삭제가 하위 컬렉션 정리까지 보장한다고 가정하지 않는다.
3. 배치마다 잔존 참조, 보상/랭킹 대사, 진행 중 세션 복구, 재전송·중복 지급 방지를 확인한다. 이상이 있으면 후속 배치를 중단한다.
4. 승인 범위 내 결과와 복구 시험을 기록하고 보존할 증빙의 위치·보존 기간을 명시한다.

완료 기준: 승인 대상과 실제 처리 결과가 일치하며 현역 기능·보상·복구 검사를 통과한다. 미확인 후보는 삭제하지 않고 보류 사유를 남긴다.

## 기록 및 승인 규칙

각 단계 기록은 `대상 → 근거 → 변경 → 검사/결과 → 미확인 사항 → 다음 조건`으로 통일한다. 상태는 미착수/조사 중/로컬 검증 완료/승인 대기/운영 확인 완료/보류로 구분한다.

로컬 읽기 전용 조사·검토안·검증 준비는 우선 진행할 수 있다. 학생 데이터 영향 변경은 구체적 영향과 검사안을 제시해 확인받으며, 운영 배포·데이터 삭제·Rules/인덱스·스케줄 변경은 별도 승인 범위를 명시한다. 이는 저장소 `AGENTS.md`의 운영 안전 규칙에 따른다. 이번 문서 작성 요청을 후속 운영 변경 승인으로 확대하지 않는다.
