# 퀴즈타운 전체 로딩 점검

2026년 10월 4일 점검. 첫 접속의 파일 전송 부담과 화면 진입 후 데이터 대기가 함께 존재한다. 특히 교실은 여러 탭의 데이터를 모두 기다린 뒤 한꺼번에 표시하는 구조여서, 가장 느린 조회가 전체 화면을 붙잡는다. 개선 우선순위는 교실의 표시와 조회 분리, 반복 조회 축소, 첫 접속 자원 경량화다.

이번 작업은 진단이다. 운영 프런트엔드·Functions·규칙·학생 데이터는 변경하지 않았고 배포·커밋·Push도 하지 않았다. 추가한 파일은 이 보고서, 진단 스크립트 2개, 측정 JSON 2개다. 비교 대상인 ‘그라운드’의 정확한 주소와 로그인 환경은 제공되지 않아 직접 비교하지 않았다.

## 측정 범위와 한계

- 실제 공개 Hosting에 격리된 Chrome으로 접속했다. 기존 사용자 세션을 가져오지 않았다.
- 인증 생성, Firestore, Storage, Functions 등 백엔드 요청을 CDP에서 차단했다. 로그인·학생 기록 읽기·자동 쿠폰 지급·접속 상태 쓰기는 실행하지 않았다.
- HTTP 캐시를 보존하기 위해 Playwright 요청 라우팅을 사용하지 않았다. 새 브라우저 컨텍스트의 첫 방문과 같은 컨텍스트의 즉시 재방문을 비교했다.
- 모든 브라우저 측정의 뷰포트는 390×844다. 모바일 모사는 다운로드 4Mbps, 업로드 1Mbps, 지연 80ms, CPU 4배 감속이다. 실제 학생 기기나 학교 Wi-Fi 측정은 아니다.
- 각 조건 1회 표본이며 평균·상위 95퍼센트 지연이 아니다. load 이후 2.2초까지 관찰한 값이다. FCP는 첫 콘텐츠 표시, LCP는 관찰 구간의 가장 큰 콘텐츠 표시이며 로그인 완료나 기능 사용 가능 시각을 뜻하지 않는다.
- 인증 후 교실·게임·코디 상점의 실제 응답 시간, 운영 Firestore 위치와 읽기 비용, Functions의 실제 실행 설정·콜드 스타트는 측정하지 않았다. 해당 부분은 코드 분석 또는 합성 재현으로 구분한다.

| --- | ---: | ---: | ---: | ---: | ---: |
| 속도 제한 없는 첫 방문 | 238ms | 940ms | 1,108ms | 1,517ms | 1,290KB |
| 같은 브라우저 즉시 재방문 | 293ms | 368ms | 368ms | 349ms | 62KB |
| 모바일 모사 첫 방문 | 415ms | 1,688ms | 3,156ms | 3,139ms | 1,295KB |
| 모바일 모사 즉시 재방문 | 114ms | 184ms | 184ms | 575ms | 62KB |

전송량은 CDP loadingFinished의 encodedDataLength 합이며 압축과 응답 헤더를 포함한다. KB는 1,000바이트다. 프레임에 실제 그리는 시점은 load 이벤트보다 늦을 수 있다. 이 공개 화면에서는 50ms를 넘는 Long Task가 관찰되지 않았다. 따라서 현 측정만으로 CPU 렌더링을 전체 서비스의 주범으로 판단할 수 없다.

첫 방문의 큰 항목은 다음과 같다.

| 항목 | 실제 전송량 | 해석 |
| --- | ---: | --- |
| 마을 배경 WebP | 416KB | 로그인 화면과 마을이 공유하는 실제 사용 배경. 숨겨진 화면의 불필요한 다운로드로 분류하지 않음 |

| Google Fonts 스타일시트 | 95KB | 폰트 파일과 별도 비용. 초기 CSS 의존성 |
| 앱 번들 | 123KB | 압축 해제 후 약 843KB. 관리자·교실·상점·퀴즈 코드 포함 |
| Firestore compat SDK | 102KB | 앱·인증·Storage·Functions SDK도 별도로 로드 |

배경과 폰트 파일·Google Fonts CSS만 약 879KB로 전체의 약 68%다. 첫 접속 최적화에서는 번들 크기만 볼 것이 아니라 글꼴 종류·글리프 범위와 작은 화면용 배경도 함께 줄여야 한다. 실제로 적용하기 전 동일 조건의 대조 측정으로 효과를 확인해야 한다.

## 화면 전환이 기다리는 지점

### 교실이 모든 데이터와 화면을 묶어서 처리함

`public/js/application/classroom-usecases.js:69`의 `getClassroomPrototypeViewData`는 설정을 기다린 다음 진행도·검토 목록·지갑·젬·학생 카드·경제 게시판을 병렬로 요청한다. 병렬 처리는 되어 있지만, 여섯 결과가 모두 끝나야 반환한다.

`public/index.html:6433`의 `renderClassroomPrototype`은 이 반환을 기다린 뒤 모든 섹션을 렌더링한다. `public/js/features/classroom-render.js:2887`은 로딩 중 모든 교실 패널에 inert를 설정한다. 같은 파일의 `renderClassroomSections`는 현재 탭뿐 아니라 학생 카드·직업·상점·은행·루틴 등 숨겨진 섹션의 렌더러도 호출한다.

합성 재현에서 설정 30ms, 일반 데이터 30ms, 경제 게시판 600ms를 부여했다. 설정 이후 일반 데이터는 시작 기준 63ms에 준비됐지만 화면용 모델은 633ms에 반환됐다. **이는 실제 운영이 633ms라는 뜻이 아니라, 한 요청의 지연이 전체 표시를 늦추는 구조를 입증한 결과다.**

권장: 홈에 필요한 승인된 요약을 먼저 표시하고 탭별 데이터를 분리한다. 각 영역에 로딩·오류 상태를 두며, 잔액과 권한이 아직 확인되지 않은 결제·보상 동작은 확인이 끝날 때까지 막는다. 이전 정상 화면을 유지하면서 필요한 영역만 갱신한다. 최근 교실 권한 오류 수정에서 지킨 ‘실패를 빈 기록이나 0원으로 보여주지 않기’를 유지한다.

### 학생 목록의 추가 조회와 서버의 큰 조회 범위

`public/js/infrastructure/classroom-repository.js:108`은 학생 카드 callable의 응답을 받은 뒤 학생별 `userLevelSummary`를 추가 조회한다. 합성 학생 22명으로 callable 1회 다음 문서 공급자 호출 22회를 재현했다. SDK 캐시와 전송 다중화가 있으므로 이것을 실제 HTTP 요청 23개 또는 과금 읽기 23개로 단정하지 않는다.

로컬 서버 `functions/index.js:5881`의 `getClassroomStudentCards`는 전체 학생 최대 500개를 조회하고 학년·반을 메모리에서 거른다. 이후 학생별 지갑·경제·프로필·칭호 요약과 학급 젬 기록을 읽는다. `functions/index.js:6282`의 `getClassroomEconomyBoard`는 권한 확인 후 직업·판매 상품·숨김 상품·배정·루틴·루틴 체크·신청 조회를 각각 순차 await하고, 이어 구매·로그·공지·금융·젬 데이터를 읽는다.

권장: 학생 카드의 필요한 요약을 한 응답에 포함하고, 학급 조건을 서버 쿼리에 반영할 수 있는지 데이터 형식·인덱스를 확인한다. 권한 검증 이후 독립적인 읽기만 병렬화하며, 경제 게시판은 탭별 조회 또는 홈 전용 요약으로 분리한다. 호출 하나로 단순히 더 많은 데이터를 합치는 방식은 피한다. 서버 함수는 미션 달성일을 조건부 저장하는 경로도 있으므로 ‘조회 함수’라는 이름만 보고 운영 벤치마크를 반복하지 않았다.

서버 부분은 로컬 소스의 사실이다. 이번 점검은 배포된 Functions 소스/리비전과의 일치까지 확인하지 않았다.

### 같은 앱 안에서 바꾸는 화면과 새 문서를 여는 화면이 혼재함

마을·학교·내 정보 등은 `public/js/features/app-view.js`에서 hidden을 전환하므로 이미 같은 문서 안에서 이동한다. 따라서 ‘퀴즈타운 전체가 매번 새로고침되기 때문에 느리다’는 설명은 정확하지 않다.

반면 하우징은 별도 문서이고 `/housing/`에서 메인 `/` 또는 `/?view=home`으로 돌아오면 메인 앱의 초기화와 회원 복원을 다시 실행한다. 하우징 자체도 인증 복원 → 연결 회원 확인 → 보유 아이템·방·상점 설정 조회를 기다린다. HTTP 캐시가 JS 재전송을 줄여도 앱의 메모리 상태와 데이터 조회까지 보존하지는 않는다.

메인 랭킹·상점은 첫 기능 설정 확인을 await한 다음 화면을 바꾼다(`public/index.html:9086`, `9099`). 설정이 캐시에 없으면 눌러도 바로 반응하지 않는 원인이 될 수 있다. 차단 정책은 유지하되 대기 중 화면 피드백이 필요하다.

권장: 자주 오가는 내 방·내 정보의 공통 화면 유지부터 검토하고, 같은 출처의 정적 자원과 화면 상태를 재사용한다. 전체 React 전환이 선행 조건은 아니다. 개별 게임은 독립 수명주기·저장·구독 해제를 확인한 뒤 통합 여부를 정한다.

### 인증 복원이 두 경로에서 겹칠 수 있음

`public/js/application/account-usecases.js:182`는 Auth 상태 콜백을 등록하는 동시에 초기 로그인 흐름을 실행한다. `public/js/features/account-data.js:350`과 `363`의 두 경로 모두 회원 복원 후 목적 화면을 연다. 회원 복원 저장소에는 완료된 프로필 재사용은 있지만 진행 중 조회 공유는 없다.

익명 로그인 완료와 Auth 콜백이 겹치는 합성 시나리오에서 회원 복원 공급자 2회, 목적 화면 호출 2회가 재현됐다. 실제 운영에서 항상 2회 요청된다는 뜻은 아니다. 완료 타이밍·기존 프로필에 따라 재사용될 수 있다. `getRestoredMemberState`는 복원 때 사용자 범위 캐시 초기화를 요청하므로 중복 복원의 영향을 함께 검증해야 한다.

권장: UID별 초기 복원 요청을 공유하고 동일 세션에서 목적 화면 진입을 한 번 처리한다. 세션 복원 완료 전 익명 로그인을 시작하는 동작도 Firebase 인증 초기화 순서와 함께 검토한다. 계정 전환·로그아웃·학생/교사 분리를 회귀 검사한다.

### 코디 상점은 카탈로그와 회원 상태를 순차 대기함

상점 iframe은 같은 메인 문서 안에서는 재사용한다(`public/js/features/shop-render.js:143`). 이 부분은 이미 유리하다.

`public/coordi-shop/dressing-room.js:1527`은 공개 카탈로그 4개를 모두 기다린 다음 회원 상태 callable을 호출하고 render한다. 주 카탈로그는 원문 약 1.96MB이며 fetch에 `cache: 'no-store'`, 실제 Hosting에도 JSON no-store가 적용된다. **1.96MB는 네트워크 전송량이 아닌 압축 해제 크기다.**

권장: 버전이 지정된 공개 카탈로그의 브라우저 캐시와 회원 상태 조회 병렬화를 검토한다. 초기 표시 목록을 줄이고 나머지는 필요할 때 처리한다. 가격·보유·구매 가능 여부는 서버의 최신 검증을 유지한다. 직접 `/coordi-shop/` 진입 측정은 로그인 안내만 표시하므로 실제 상점 속도 수치로 쓰지 않았다.

## 캐시와 서버에 대한 판정

실제 응답에서 메인 HTML은 no-store, JS/CSS는 `max-age=300, stale-while-revalidate=3600`, SDK는 약 1년 캐시, 배경 이미지는 1시간 캐시였다. 즉시 재방문의 전송량이 1.29MB에서 62KB로 감소한 것도 확인했다. 5분이 지났다고 모든 JS를 매번 전체 다운로드한다고 해석해서는 안 된다.

HTML은 작은 앱 진입점으로 줄여 최신 버전을 확인하게 하고, 변경 시 URL이 바뀌는 정적 파일에 긴 캐시를 적용하는 방향이 적절하다. 지금처럼 수동 버전 문자열과 같은 파일명 덮어쓰기가 혼재한 상태에서 무조건 캐시 기간만 늘리면 업데이트가 늦게 반영될 수 있다. 캐시 정책의 근거는 [Firebase Hosting 공식 문서](https://firebase.google.com/docs/hosting/manage-cache)다.

클라이언트 Functions 지역과 로컬 서버 REGION은 모두 `asia-northeast3`다. 지역 불일치가 확인된 것은 아니다. 로컬 함수 정의에 minInstances 설정은 없지만 운영 콘솔의 실제 설정은 조사하지 않았다. 콜드 스타트는 가능한 추가 원인이며 이번 측정으로 확정하지 않는다. 인증된 요청의 첫 호출·반복 호출 시간을 비교한 뒤 필요한 함수에 한해 검토한다. 최소 인스턴스에는 유휴 비용이 있고 확장 인스턴스의 콜드 스타트까지 모두 없애지는 않는다. [Firebase Functions 공식 문서](https://firebase.google.com/docs/functions/manage-functions#control_scaling_behavior) 참고.

## 이미 개선되어 있는 부분

- 9월 16일 배경 WebP 전환과 일부 광장 이미지 지연 로딩, 선택한 게임 랭킹만 조회하는 개선 이력이 있다.
- 내 정보는 보상 상태를 기본 프로필과 분리하고 30초 캐시·진행 요청 공유·상세 펼침 시 조회를 적용했다.
- 이벤트는 60초 캐시·진행 요청 공유·기존 카드 유지·입구 포커스 선조회를 적용했다.
- 하우징 가구 묶음에는 버전별 IndexedDB 캐시가 있다. 첫 방문과 같은 버전 재방문은 비용이 다르다.

이전 개선을 다시 신규 문제로 보고하지 않는다. 다만 해당 개선이 교실·로그인 복원·독립 게임 이동까지 일괄 적용된 것은 아니다.

## 운영본과 로컬의 차이

공개 HTML·번들·styles.css는 현재 로컬과 전체 해시가 다르다. 공개본에는 하보 명예의 전당 링크, 하우징 상점 이동 전 설정 확인, 로그인 복원 후 쿠폰 확인 등이 있고 로컬에는 다른 상점 전시·삼각형 게임 메뉴 변경이 섞여 있다. CSS와 파일 버전 문자열에도 차이가 있다. 기존 부분 배포 기록과 부합하는 차이이며 이번 점검이 만든 차이는 아니다.

이번 핵심 분석에 사용한 교실 유스케이스·저장소·렌더러, 인증 유스케이스·데이터, 상점 렌더러는 **실제로 브라우저가 받는 운영 번들 내부에 로컬 소스가 그대로 포함됨**을 확인했다. 하우징 HTML/app/data, 코디 bridge/dressing-room/주 카탈로그도 운영본과 로컬 해시가 일치했다. 개별 JS URL의 일치만으로 실제 실행 번들의 일치를 추정하지 않았다.

부가 확인: 공개 `/fraction-world/`는 404였다. 이 요청의 측정은 오류 페이지의 시간이며 게임 성능 평가에서 제외한다. 로컬 파일 존재를 운영 배포 완료로 간주하지 않는다. 요청 범위 밖이므로 배포하지 않았다.

## 권장 실행 순서

| 순서 | 작업 | 성공 판정 |
| --- | --- | --- |
| 1 | 교실 홈·현재 탭 우선 표시, 영역별 조회·오류·갱신 | 느린 다른 탭 때문에 준비된 영역이 막히지 않고, 실패가 가짜 0/빈 기록으로 보이지 않음 |
| 2 | 학생별 후속 읽기 축소, 경제 서버의 독립 읽기 병렬화·응답 범위 분리 | 같은 데이터/권한으로 공급자 호출 수와 응답 대기 감소. 필요한 인덱스·권한 검증 유지 |
| 3 | 글꼴·모바일 배경 최적화, 관리자/교실 코드 분리 | 첫 방문 전송량·FCP/LCP 개선을 동일 조건에서 반복 측정 |
| 4 | 인증 복원 중복 제거, 내 방/내 정보 왕복 상태 유지 | 한 UID 복원 중 요청 공유, 중복 목적 화면 진입 방지, 계정 전환 정상 |
| 5 | 코디 공개 카탈로그 버전 캐시와 상태 조회 병렬화 | 반복 진입의 카탈로그 전송 감소, 구매 검증·가격 최신성 유지 |
| 6 | 인증된 실사용 경로 측정 후 필요한 서버 설정 조정 | 첫 호출/반복 호출을 구분하고 개선 전후 중앙값·상위 지연 및 비용 비교 |

재방문 탭의 즉시 피드백은 100ms 안팎을 개발 목표로 삼을 수 있으나 현재 달성 수치나 보장치는 아니다. 학생 기기에서 클릭 → 화면 반응 → 필수 데이터 준비를 따로 측정해야 한다. 서버·학생 데이터 영향 변경은 저장소 승인 규칙에 따라 구체적인 영향과 검증을 먼저 제시한다.
