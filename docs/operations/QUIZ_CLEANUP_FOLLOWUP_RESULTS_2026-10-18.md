# 퀴즈 정리 후속 단계 실행 기록

기준: [6~12단계 계획](QUIZ_CLEANUP_FOLLOWUP_PLAN_2026-10-18.md). 아래 6~9단계는 배포 전 로컬 실행 기록이다. 이후 사용자 승인으로 함수 5개와 Hosting을 배포했으며 최신 상태는 [배포 기록](QUIZ_CLEANUP_DEPLOYMENT_2026-10-18.md)을 따른다. 데이터 삭제와 학생 데이터 조회는 하지 않았다.

- 공개 Hosting 7파일은 최초 조사 이후 모두 동일했다. 현재 로컬과 운영의 차이는 유지되고 있으므로 로컬 전체 배포는 하지 않는다.
- 운영 함수 목록 130개를 읽기 전용 확인했다. 관련 5개 함수의 소스를 다운로드하고 다운로드 전후 updateTime이 같은지 확인했다. 환경 변수·인증값은 문서 증빙에 포함하지 않았다.

구형 집계 제거 전 index와 현재 index를 각각 독립 에뮬레이터에서 실행했다. 같은 회원·지갑·부스트(0.5)·정답 시나리오의 아래 결과 및 일일/주간 XP 한도 누적치가 정확히 일치했다. 실제 학생 데이터는 사용하지 않았다.

| --- | ---: | ---: | ---: |
| 첫 정답 동시 중복 요청 | 1 | 2 | 101.5 |
| 일일 보상 한도 도달 | 50 | 20 | 115 |

| 주간 XP 499→500 부분 지급 및 이후 지급 제한 | 63 | 38 | 118 |

교실 포인트는 시작 잔액 100을 포함한다. 기존 구현은 XP를 지급하는 경로에서 코인 미러를 처리하므로 일일 XP 한도 이후 모든 코인이 포인트로 미러되는 구조가 아니다. 이번 변경은 이 동작을 수정하지 않았다. 과목 검사 전 일일 한도만 테스트 목적으로 재설정했으며 주간 누적은 유지했다. 추가로 주간 XP 누적을 499로 설정해 +1만 지급되는 경우와 500 도달 후 XP 0 지급을 확인했다. 모든 비교 시점의 결과가 변경 전후 일치했다.

구형 집계는 baseline 실행에서 새 문서 생성이 확인되고, 수정 후 실행에서는 사전 삽입 문서의 updateTime 불변·전체 1개 유지가 확인됐다. 테스트에 교실 포인트 단언과 비교 출력 기능을 추가했다.

사용자가 **“현재 타운만 사용 — 구형 기능은 종료”**라고 확인했다. 영향과 검증 방법을 안내한 뒤 `rewardGeneratedSubjectAnswer`의 `dailyUsage` 읽기 1회·쓰기 1회를 제거했다. 연습 보상 함수와 랭킹 무보상 반환은 유지한다. 에뮬레이터 검사는 기존 사용량 문서의 updateTime 불변과 문서가 없던 경우 신규 생성 없음, 코인·XP·랭킹·중복 처리를 확인한다. 구형 callable은 기존 호환 응답을 유지하며 새 과목의 정답은 더 이상 구형 해제 횟수에 반영되지 않는다. 기존 문서 삭제나 외부 호출 로그 조사는 하지 않았다.

## 8단계 — 내부 헬퍼 10개 제거

삭제 전 서버 선언 외 참조, public/test/script 참조, 동적 eval/export 경로를 확인했다. 브라우저의 동명 함수는 다른 스코프이므로 유지했다. 제거 대상은 외부 export가 아닌 내부 함수다.

- `getSeasonEventsUpdateLock`, `getTodayQuizIds`
- `mirrorDjCoinRewardToClassroomPoint` — 현행 `applyLevelXp`의 포인트 미러 경로는 유지
- `getRecordAreaKey`, `buildEventQuestRows`
- `loadMemberPracticeRecords`, `loadEventClaimMap`, `loadEventProgressMap`, `loadClassEventProgress`
- 서버의 `getTodayQuizNoticeText`

총 222줄 제거. 실제 미호출 코드였으므로 이 줄 수를 운영 DB 읽기 절감으로 계산하지 않는다.

보존 항목과 근거:

- `publicSeasonEvents`: `scripts/maintenance/prepare-integrated-season.py`가 배포 준비 시 이름으로 추출한다. 최초의 ‘선언만 존재’ 판정은 운영 스크립트까지 포함한 삭제 근거가 아니었다.
- 시즌 관리자 UI: controller → shell → renderer/store 연결이 남아 있다. 호출 연결과 호환 화면 종료를 묶어 정리해야 하며 이번 내부 헬퍼 제거에 섞지 않았다.
- `updateEventQuestProgressForKinds` 및 새로 드러난 하위 의존성: 기존 오프라인 감사의 구형 쓰기 재현에 사용된다. 감사 목적 변경과 함께 별도 정리한다.
- 인증 함수, 예약 함수, 성장 트리거 및 모든 callable export는 유지한다.

## 9단계 — 반복 조회 보완과 무손실 이미지 전환

### 9-A 적용

설정 신선도 조회는 로그아웃·숨김 탭에서 시작하지 않는다. 같은 회원의 진행 중 요청은 공유하고, 탭이 다시 보이면 즉시 확인한다. 계정 전환/로그아웃 이후 도착한 응답은 현재 UI에 적용하지 않는다. 실패 후에는 다음 조회가 가능하도록 요청 상태를 해제한다.

실제 shell 함수로 숨김/로그아웃 0조회, 중복 1조회, 재진입, 오류 후 재시도, 계정 전환의 늦은 응답 무시를 검증했다. `test:infrastructure`에 3개 회귀 검사를 추가했다. 과목/퀴즈왕 캐시는 추가하지 않았으며 종합 랭킹의 정확성 정책은 유지한다.

### 9-B 적용과 제외 기준

- 현재 인기 팩 551개 이미지의 원본은 총 385,232,240바이트다. PNG 123개, JPEG 408개, WebP 20개다.
- 가장 큰 JPEG를 무손실 재인코딩하면 13,485,055→16,632,480바이트로 증가하여 JPEG 일괄 변환을 채택하지 않았다. 리사이즈나 손실 압축은 하지 않았다.
- PNG 123개 중 104개는 서버 디코딩 픽셀 일치 검사에서 제외했다. 남은 19개 중 5개도 실제 Chrome 디코딩 결과가 달라 제외했다. 실패를 허용 오차로 덮지 않고 원본 URL을 유지한다.
- 최종 **14개**는 서버와 Chrome 모두 원본/파생본의 디코딩 픽셀 및 해상도가 완전히 같다. 60,414,049→42,089,904바이트로 **18,324,145바이트(약 18.3MB)** 줄었다.
- 전체 카탈로그가 참조하는 파일 합계는 366,908,095바이트다. 이것은 한 번의 방문 전송량이나 실제 청구 절감액이 아니다. 원본 보존 때문에 저장소 점유는 파생본 약 42.1MB만큼 증가한다.
- `build-popular-lossless-images.js`가 파생본과 manifest를 만들고, 정상 `build-popular-quiz.js`가 원본 SHA-256 검증을 유지하면서 검증된 파생 URL만 선택한다. 원본 출처 해시 `sha256`은 유지하고 표시 파일 해시 `imageSha256`을 분리했다.
- 새 카탈로그 버전은 `lossless-png-v1` 접미사를 사용한다. 구버전 세션의 저장된 원본 URL과 콘텐츠 버전은 유지하며 재개/답변 회귀 검사를 추가했다.
- 5개 브라우저 불일치 제외는 원본 해시와 함께 `lossless-policy.json`에 고정했다. 원본이 바뀌면 재검토 없이 제외 근거를 재사용하지 않는다. 전체 재생성 후 정상 카탈로그 검사도 통과했다.
- 감사 스크립트도 표시 URL과 원본 출처/구세션용 URL을 구분한다. 표시 URL에서 빠졌다는 이유로 원본을 삭제 후보로 오판하지 않는다.

시각 확인용 원본/파생본 비교 화면과 14쌍의 브라우저 픽셀 검사 결과를 남겼다. 원본 파일·외부 출처·현재 운영 파일은 수정하지 않았다.

## 10~12단계 — 배포 전 준비 기록 (당시 상태)

운영 변경에는 별도 승인이 필요하다. 사용자 소비 종료 확인과 로컬 이미지 전환은 반영했다. 운영 함수별 원본에서 관련 함수만 교체한 5개 후보 패키지 및 운영 Hosting에서 문맥 일치로 적용한 후보를 준비했다. 기존 다른 로컬 수정은 포함하지 않았고 이번에는 배포하지 않았다.

배포 준비 시 필요한 대상은 `subjectQuizAction`, `popularQuizAction`, `grantPracticeReward`, `grantRankingCompleteXp`, `adminGetQuizQualityAudit` 및 변경된 Hosting 파일이다. 함수마다 배포 소스가 다르므로 검증된 변경 부분만 옮긴 후보를 만들고 검사해야 한다. 배포 순서는 과목/보상/랭킹/관리자 서버 → Hosting(새 이미지 포함) → 인기 서버 카탈로그다. 새 랭킹 API는 프런트보다 먼저, 새 이미지 파일은 이를 반환하는 인기 서버보다 먼저 제공해야 한다. 이 목록은 배포 승인이나 검증 완료 후보를 뜻하지 않는다.

운영 쓰기 중단과 최근 갱신 관찰이 아직 없으므로 삭제 manifest에 확정 ID를 넣을 근거가 없다. 현역/혼합 랭킹·보상 원장·중복 처리 표식·출제 deck은 보존한다. 데이터 삭제·TTL·Rules/인덱스·스케줄 변경은 미실행이다.

## 공유 작업 트리의 후속 변경

최종 해시 대조 중 같은 `functions/index.js`와 `public/index.html`에서 다른 작업의 하우징 쿠폰 설명 수정, 이어서 쿠폰 폐지 기능 변경을 발견했다. 해당 변경은 덮어쓰지 않았다. 현재 공유 작업 트리 전체를 이번 검사로 검증했다고 주장하지 않는다.

검증 당시 코드와 이번 patch를 `/tmp/quiz-cleanup-followup-20261018/verified-snapshot/`에 고정했다. 중간에 섞였던 쿠폰 설명 주석(2장→10장)도 정리 patch에서는 제외하고 초기 기준 주석을 유지했다. 실행 코드에는 차이가 없다. 운영 후보 재생성 도구는 이 고정본과 증빙 해시를 요구하며 현재 공유 파일의 추가 수정을 자동 포함하지 않는다.

고정본으로 다시 생성한 함수 5개 후보의 변경 파일과 Hosting 20파일이 앞서 테스트한 후보와 바이트 단위로 동일함을 확인했다. 후보 생성 도구 보완 중 변수명 충돌을 수정한 뒤 재생성을 통과했다. 공유 작업 트리의 하우징 변경은 별도 작업의 검증 범위이며, 배포 직전 최신 운영 릴리스/함수 버전을 다시 대조해야 한다.
