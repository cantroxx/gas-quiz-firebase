## 1. 핵심 결론

제품 코드를 로컬에서 수정하고 필수 `npm run check`를 통과했다. **운영 배포·커밋·푸시·서비스 이전은 하지 않았다.** 운영 데이터·규칙·설정을 수정하는 명령은 실행하지 않았다. 다만 기존 공개 검사에서 자동 익명 인증이 시작되는 운영 페이지를 연 안전상 문제가 있어 6절에 별도로 기록했다.

- **관리자:** 대시보드만 먼저 읽고 회원 목록은 해당 탭에서 읽는다. 최고 관리자 진입 뒤 시작하던 추가 8개 작업을 제거했다. 운영 점검과 퀴즈 품질 점검은 기존 ‘점검 실행’ 버튼을 눌러야 시작한다. 대시보드 서버의 독립 조회도 권한 확인 뒤 병렬로 시작한다.
- **교실:** ‘학교 → 우리 교실’과 관리자 ‘교실로 이동’의 `classroom-view`를 개선했다. 오늘 화면은 본인 정보·포인트·퀘스트만 기다린다. 학생카드·마켓·은행·관리 화면은 해당 탭에서 조회·렌더한다. 학생 입장코드 확인은 유지했다.
- **코디 상점:** 설정 확인 전에 상점 뼈대와 진행 안내를 먼저 표시한다. 상품과 회원 정보의 기존 병렬 조회, 같은 계정의 iframe 재사용은 유지한다. 미리보기의 서버 인증은 매번 수행하면서 불필요한 잔액·보유 상품 조회를 제거했다.
- **대기를 없앤 것과 옮긴 것을 구분해야 한다.** 교실 마켓과 관리자 회원 목록의 첫 조회는 해당 탭을 처음 여는 시점으로 이동한다. 이후 재진입은 캐시를 활용한다. 상점 외부 렌더 자체가 빨라졌다는 증거는 없다.

작업 중 이번 수정에 포함되지 않은 교실 SVG 그림 교체·모바일 CSS·기존 UI 검사 보완도 확인했다. 작성자는 추정하지 않고 보존했다. 인과 비교를 위해 이 중 **그림 함수와 CSS 변경은 비교용 before/after 양쪽에 동일하게 반영**했다. 원본 시작 스냅샷은 그대로 남겼다. 이 그림·CSS 변경의 효과를 이번 성능 개선 실적으로 계산하지 않는다.

- macOS 26.6.2 arm64, 기존 진단과 같은 Apple M2 Pro 컴퓨터, Chrome 154.0.8037.95, Playwright 설치본 사용, headless 1440×1000, CPU·회선 감속 없음. 별도 패키지 설치 없음.
- 역할·샘플마다 새 격리 브라우저 컨텍스트. 기존 사용자 쿠키·로그인·브라우저 데이터는 지우거나 복사하지 않았다. 각 컨텍스트에서 첫 진입→재진입→다른 shell 화면을 3회 왕복 후 재진입. 역할별 3표본, 버전당 45개 주 진입 결과.
- ‘왕복’은 화면 shell 토글이다. 다른 화면의 실제 데이터 로더·퀴즈·저장 작업까지 실행한 장기 사용 시험은 아니다. 회원·교실 마켓 탭은 별도로 실제 로컬 탭 코드도 실행했다.
- 모든 측정 브라우저 요청은 로컬 파일·합성 응답으로 처리. 관리자 80명, 교실 22명, 퀘스트·잔액은 합성 자료. Firebase SDK 인증·운영 서버·리전·네트워크·쿼터·최초 함수 실행은 측정하지 않았다.
- 주입 지연: 대시보드 200ms, 회원 목록 300ms, 추가 작업 400ms/점검 800ms; 교실 설정·일반 읽기·본인 읽기 50ms, 경제 게시판 600ms, 학생 코드 검증 100ms; 상점 설정 150ms, status와 공개 JSON 각각 400ms, 미리보기 800ms. 개선 전후 같은 조건이다.
- 상점은 로컬 공개 카탈로그를 사용하고 미리보기는 1px 합성 이미지다. 실제 아바타 디코딩·외부 렌더·염색 처리의 성능을 대표하지 않는다. 재진입은 메모리 캐시·iframe 재사용 시험이며 HTTP 캐시 성능 시험이 아니다.
- 첫 시각 반응과 뼈대는 실제 DOM 전환 뒤 두 번의 requestAnimationFrame으로 근사했다. GPU 픽셀 캡처·INP·표준 TBT가 아니다. 핵심 데이터와 조작 가능은 필요한 데이터/버튼 상태와 연결했다. 교실은 `inert` 해제와 오류 여부, 상점은 status·상품·성별 준비를 확인했다. 거래를 운영에서 실행하지 않았다.
- 학생 교실의 첫 뼈대는 입장코드 화면이다. 코드 입력은 자동화하고 사람 입력 시간을 포함하지 않았다. 상점 성별 선택도 준비 직후 브라우저 내부에서 자동 처리했다. 자동화 도구의 polling 시간을 조작 가능 시간으로 사용하지 않았다. 이전 진입의 예약된 페인트 콜백은 새 측정에 들어가지 않게 구분했다.
- ‘추적 작업 완료’는 이번 진입이 시작한 공급자 작업과 핵심 표시가 완료되는 시점이다. 지연된 숨은 탭이 모두 준비됐다는 뜻도, 무한 실시간 연결까지 끝났다는 뜻도 아니다. 상점은 별도로 이미지 완료 상태를 확인했다.

[원자료·환경·소스 해시](performance-improvements-2026-10-07/README.md)에 재현 절차와 버전 정보를 남겼다. 측정 뒤 변경된 제품 코드는 교실 form 한 줄의 후행 공백 제거뿐이며 정식 번들을 다시 빌드했다. 실행 동작의 변경은 아니다.

## 5. 요청·데이터·렌더 비용

**공급자 호출은 HTTP 요청 수가 아니다.** 관리자·교실 공급자는 실제 코드의 의존성을 합성 함수로 주입했다. 상점만 실제 브라우저 요청을 가로채 응답했으며 운영 전송량은 아니다.

| 첫 진입 | 공급자 호출 전→후 | 합성 응답 본문 B 전→후 | 측정한 동기 렌더 ms 전→후 | DOM 노드 전→후 |
| --- | ---: | ---: | ---: | ---: |
| admin · classAdmin | 2→1 | 8414→76 | 2.0→0.3 | 2495→1536 |
| admin · superAdmin | 10→1 | 8430→76 | 2.0→0.4 | 2577→1538 |
| classroom · student | 7→5 | 2129→644 | 32.2→12.1 | 2410→1547 |
| classroom · teacher | 7→4 | 2131→644 | 37.9→11.7 | 3038→1536 |

위 바이트는 JSON 직렬화한 **합성 공급자 반환값**이다. 관리자 추가 작업의 응답은 빈 합성 객체라 실제 목록·로그 크기를 재현하지 않는다. 운영 절감 비율로 사용하지 않는다. DOM 수는 해당 시점 메인 document 전체이며 숨은 앱 shell도 포함한다. 렌더 시간은 계측한 동기 JS 함수의 합이고 스타일 계산·페인트·전체 메인 스레드 시간은 아니다. 코디 iframe 렌더 비용은 따로 계측하지 않았으므로 0ms로 해석하지 않는다.

코디 첫 진입은 두 버전 모두 브라우저 요청 43개(status 1, preview 1, 공개 JSON 4 포함), 재진입 추가 요청 0개였다. 가로채 공급한 무압축 본문 총량은 3,273,817→3,274,264 B였다. 이는 로컬 JS·카탈로그·그림·합성 status를 합한 값이며 실제 운영 압축 전송량이 아니다. 상품 경량화나 iframe 재사용을 이번에 새로 구현했다고 계산하지 않는다.

학생카드는 클라이언트 callable 1개 뒤 학생 수 N개의 레벨 추가 읽기에서, 레벨을 포함한 callable 1개로 바뀐다. 서버에서는 같은 N개 레벨 문서를 1개 getAll 그룹으로 읽는다. 실제 RPC 수·압축 바이트·요금은 측정하지 않았다. 오늘의 본인 조회는 전체 학생카드와 경제 응답을 가져오지 않는다.

초기 브라우저 검사에서는 지연 렌더로 아직 생성되지 않은 관리 DOM 접근이 실패했다. null 대응을 수정한 뒤 전체 검사를 다시 통과했다. 계측 스크립트의 경로 해시·예약된 페인트 콜백 문제도 수정하고 이전 중간 결과를 최종 표에서 제외했다. 합격으로 표시한 것은 수정 후 실제 실행한 검사다.

**검사 안전 문제와 조치:** 앞선 기존 `npm run check` 3회(최초 교실 검사 실패 포함)의 공개 smoke는 운영 main·wordbattle·housing 페이지를 열었다. publicOnly는 학생 로그인 버튼을 누르지 않는 모드였지만 **Firebase API를 차단하는 모드는 아니었다.** main 초기화와 wordbattle 시작 코드에는 자동 `signInAnonymously()`가 있어, 격리 브라우저의 익명 Auth 계정이 생성됐을 가능성이 있다. 관련 경로는 `public/js/features/account-data.js:76`과 `public/wordbattle/main.js:174`다. 당시 요청/응답·Auth 감사 로그를 수집하지 않아 실제 성공 여부와 개수를 확인하지 못했다. 로그 파일 시각상 관련 검사 구간은 대략 **2026-10-07 16:50–17:09 KST**다. 학생 로그인·구매·장착·코인 지급·퀴즈 제출은 실행하지 않았고, 새 격리 컨텍스트에 학생 연결 정보는 없었다. 운영 쓰기 영향이 전혀 없었다고 단정하지 않는다.

이를 발견한 후 추가 운영 접근을 중단했다. 익명 계정을 임의 삭제하거나 운영 로그·학생 목록을 대량 조회하지 않았다. 필요한 추가 확인은 운영 담당자가 해당 시간대의 익명 Auth 생성 기록을 **읽기 전용으로 확인**하는 것이다. 생성됐더라도 삭제는 별도 승인 대상이다.

재발 방지를 위해 `scripts/smoke/public-shell-fixture.js`를 추가하고 기존 `browser-smoke-test.js`의 publicOnly를 변경했다. 이 모드는 이제 가상 origin에서 **로컬 제품 파일·설치된 Firebase compat SDK·합성 demo 설정**을 제공하며, 모든 외부 요청과 POST/API 요청을 차단한다. 서비스워커도 차단한다. 차단 때문에 예상되는 네트워크 오류만 구분하고 다른 page error 검사는 유지한다. 외부/API 차단과 로컬 소스 공급을 새 회귀 검사로 확인했다. 마지막 `npm run check`는 이 모드로 통과했다. 운영 인증·backend 연결 성공을 검사한 결과가 아니다.

개선 전후 성능 측정은 처음부터 별도의 전면 route interception을 사용했으므로 이 공개 smoke 문제와 별개로 모두 합성/오프라인 환경이었다. 거래·보상 검사는 합성 자료/로컬 demo 에뮬레이터만 사용했다.

서버 관리자 권한·학생 연결·학급 범위·입장코드 정책, 랭킹 저장·집계 로직, DJ코인 지급/차감 정책은 변경하지 않았다. 새 home 경로는 인증 후 읽기 전용이며 권한 거부 시 콘텐츠 조회 0개를 검사했다. `firestore.rules`, `firestore.indexes.json`, `firebase.json`은 시작 스냅샷과 동일하고 Storage 규칙도 변경이 없다. 기존에 이미 수정되어 있던 규칙·인덱스 파일은 원복하지 않았다.

미실행: 운영 인증 상태에서의 세 화면 전환, 실제 Firebase TTFB/쿼터/리전/최초 실행 로그, 운영 거래, 실제 외부 코디 렌더 시간, 실제 기기 모바일 지연 비교, 장시간 구독·메모리 누적 프로파일, 실사용자 INP. 인증 세션·쓰기 승인·실제 서버 관찰 없이 이를 통과했다고 표시하지 않는다. 이번에 추가한 이벤트는 bootstrap 시 한 번 연결하며 진입마다 구독/타이머를 새로 추가하지 않는다. 장시간 누수 부재의 증명은 아니다.

## 7. 운영본과 로컬 차이·남은 병목·Firebase 판단

이전 진단에서 운영 main HTML/번들과 핵심 호출 경로를 대조했지만 로컬 교실 render/workspace는 이미 운영본과 달랐다. 이번 작업은 여기에 로컬 성능 변경을 추가했다. **운영 Functions의 실제 배포 리비전이 이 로컬 코드와 같다고 확인하지 않았으며, 이번 변경은 운영에 반영하지 않았다.** 그라운드(`https://growndcard.com`)와의 기존 공개 첫 화면 비교도 로그인 후 관리자·교실·상점의 동일 작업 비교가 아니므로 달성 목표 판정에 사용하지 않는다.

남은 병목은 다음과 같다.

1. 마켓·은행 등은 아직 경제 게시판의 큰 공통 응답을 받는다. 20개 읽기 중 탭별로 어떤 항목이 실제로 지배하는지 운영 읽기 시간과 응답량이 필요하다. 이 결과를 보고 다음 단계에서 경제 응답 분할을 검토한다.
2. dashboard의 users/credential 수와 일일 기록 1,000 제한은 유지됐다. 독립 조회 병렬화는 순차 대기만 줄이며 읽기 양이나 통계 제한을 해결하지 않는다. 회원 탭까지 쓰면 users 일부 중복 읽기는 남는다.
3. 학생 입장코드 확인 대기와 본인 정보 조회는 남는다. 이를 생략해 보이는 속도를 높이지 않았다.
4. preview의 외부 렌더·이미지 디코딩, 실제 카탈로그/그림 전송량은 합성 실험으로 판단할 수 없다. 인증 조회 2개 감소를 외부 렌더 단축으로 환산하지 않는다.
5. 관리자 캐시는 15초 동안 화면 자료가 낡을 수 있다. 외부 관리자에 의한 변경은 명시 갱신/만료 후 반영하며 거래·수정은 서버가 다시 검증한다.

**권고는 Firebase를 유지한 상태에서 이번 변경을 검토하고 실제 운영 읽기 경로를 측정하는 것이다.** 프런트엔드의 과도한 초기 작업과 조회 순서 문제는 확인했지만 공급자 자체의 지속적 지연을 입증하지 못했다. 이전으로 해결할 병목이나 이전 후 속도 보장은 제시할 수 없다. 최소 조회·캐시 이후에도 서버 구간이 반복적으로 지배하고, 실제 권한/거래 일관성을 유지한 대안의 동등 부하 시험이 더 낫다는 증거가 생길 때 이전을 별도 검토한다. 비용·서비스 한도·리전 이점은 이번 자료만으로 판단하지 않는다.

운영에서 남은 확인의 최소 절차: 배포 검토 후 사용자가 제공하는 **기존 인증 세션**에서 관리자 dashboard/members, 코디 status/preview의 읽기 경로만 1회부터 확인한다. 운영 점검 두 개·기능 설정 탭은 열지 않는다. 교실은 현재 운영본의 자동 경제 호출 여부부터 다시 확인하고, 새 읽기 전용 home이 실제 배포된 경우에만 오늘 화면을 대상으로 한다. 경제 탭은 미션 달성일 조건부 쓰기가 남는다. 새 로그인에는 계정 연결/접속 기록 등 쓰기가, 기존 교실 전체 진입에는 경제 부수 쓰기가 생길 수 있으므로 **새 로그인·경제 탭 측정은 예상 쓰기 범위를 확인받은 뒤 별도 작업**으로 한다. 요청 본문·학생 식별자는 저장하지 않고 익명 시간·개수·바이트만 기록한다.

## 8. 배포 전 검토와 되돌리기

이번 단계에서는 배포 준비 명령이나 배포를 실행하지 않았다. 승인 후 다음을 검토한다. 제품 성능 변경을 되돌리더라도 **공개 검사의 오프라인 차단 보완은 유지**해야 한다. 구현 패치에는 검사 도구 변경도 포함되어 있으므로 전체를 무조건 역적용하지 않는다.

- 범위: main HTML/정식 app bundle, dressing-room, `adminGetDashboard`, `getClassroomStudentCards`, preview가 사용하는 commerce 모듈과 관련 Functions. 혼재한 다른 미커밋 변경까지 전체 배포하지 않도록 시작 스냅샷·구현 패치와 대조한다.
- 호환 순서: 서버의 memberOnly/레벨 포함 응답을 먼저 확인한 뒤 프런트엔드를 전환한다. 구서버 fallback은 유지했지만 본인 자료가 없는 관리자/숨김 학생은 안전하게 로딩 오류가 나므로 프런트만 먼저 배포하면 안 된다.
- Hosting JS 캐시는 현재 `max-age=300, stale-while-revalidate=3600`이다. 승인된 배포 때 main bundle와 coordi script의 버전 URL 및 실제 응답을 확인해 새 HTML과 오래된 JS가 섞이지 않도록 한다. 이번에 Hosting 설정을 바꾸지 않았다.
- 최고 관리자 공지 동기화가 기능 설정 탭으로 이동한 영향, 오늘 화면의 상세 정보 ‘보기’ UX, 첫 회원/마켓 탭으로 이동한 대기, 학급 관리자/최고 관리자·학생/교사 접근 범위를 검토한다.
- 되돌릴 때 Git HEAD 전체 복원이나 `git reset --hard`를 사용하지 않는다. [이번 구현 패치](performance-improvements-2026-10-07/implementation.patch)와 시작 해시로 **이번 변경만** 역적용하고 정식 번들을 다시 빌드한다. 충돌하면 다른 작업을 보존하며 수동 대조한다. 새 진단/검사 파일은 별도로 유지하거나 제거한다. 데이터 마이그레이션은 없으므로 데이터 복원은 필요 없다. 향후 이미 배포했다면 이전에 승인한 Hosting/Functions 버전을 짝으로 되돌리는 별도 승인 절차가 필요하다.

먼저 검토할 개선 3개는 (1) 관리자 초기 작업 분리와 조회 병렬화, (2) 교실 오늘 데이터와 탭 렌더 분리, (3) 상점 즉시 안내와 preview 최소 읽기다. 모두 로컬 구현·검증을 마쳤다. 후속 비교는 이 보고서의 동일 합성 자료·지연·브라우저/역할/진입 순서와 3회 중앙값·범위를 유지하고, 승인된 운영 읽기 실측을 별도 표로 추가한다. 배포하지 않은 상태로 마무리한다.
