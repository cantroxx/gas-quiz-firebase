# DJ48 퀴즈타운 종합 성능 진단 — 2026-10-07

## 1. 비개발자도 이해할 수 있는 핵심 결론

**개선 우선순위를 관리자 → 교실 → 상점 진입으로 수정한다. 배경·글꼴 경량화는 후순위다. Firebase 이전 필요성은 유보한다.** 추가 진단에서 불필요한 관리자 초기 작업, 교실 전체 데이터 완료를 기다리는 조작 잠금, 상점 설정·미리보기의 별도 대기 경로를 확인했다. 다만 운영 로그인 후 서버 시간은 아직 없어 세 화면의 지연을 ‘Firebase 자체 성능’이나 특정 원인 하나로 확정할 수 없다.

- **코드에서 확인 + 합성 측정:** 최고 관리자는 대시보드/회원 목록 뒤 숨은 기능 8개를 자동 로드하고 재진입 때도 반복한다. 운영 점검은 여러 큰 컬렉션을, 퀴즈 점검은 퀴즈별 문항을 읽는다. 반 관리자는 기본 2개다. 이 차이를 배경 이미지보다 먼저 다룬다.
- **코드에서 확인 + 합성 측정:** ‘교실’은 학교의 우리 교실 화면이다. 일부 정보가 먼저 보여도 경제·학생카드 등 전체 모델을 기다릴 때 조작이 잠긴다. 데이터 캐시는 이미 있으며, 학생은 재진입 때 입장코드 확인 때문에 settings 강제 갱신과 검증이 다시 발생한다.
- **코드에서 확인 + 합성 측정:** 마을 코디 상점은 상품과 회원 상태를 이미 병렬 조회하고 iframe을 재사용한다. 캐시 없는 flags 조회는 화면 전환을 늦추며, 상품 준비 뒤 성별 선택과 외부 아바타 렌더가 별도다. 교실 안 마켓과 혼동하지 않는다.
- **안전 경계 정정:** 상점 status/preview는 확인한 서버 코드에서 운영 데이터 쓰기가 없다. 반면 최고 관리자 진입의 `adminGetFeatureFlags`에는 공지 동기화 쓰기, 교실 경제 조회에는 미션 달성일 쓰기가 숨어 있다. 로그인 후 전체를 일괄 제외하지 않고 호출별 경계를 특정했다.
- **측정의 범위:** 관련 실제 UI 코드와 합성 데이터로 총 45개 최종 진입 표본(각 조건 3회)을 수집했다. 운영의 관리자·학생 인증 세션은 확보하지 못해 실제 Functions/Firestore 지연은 미측정이다. 합성 응답 지연을 운영 속도로 표시하지 않았다.
- 기존 공개 첫 방문 LCP(퀴즈타운 desktop 0.956초, 제한 환경 3.036초)는 초기 리소스 개선 근거로 보존한다. [그라운드](https://growndcard.com/)와의 비교도 공개 소개 화면에 한정되며, 관리자·교실·상점의 로그인 이후 쾌적함을 비교한 결과가 아니다.

이번에 제품 코드·운영 데이터·Rules·인덱스·운영 설정을 변경하지 않았다. 배포·커밋·푸시·백엔드 이전도 실행하지 않았다. 새 산출물은 이 보고서와 `docs/operations/performance-2026-10-07/`의 진단 자료다.

### 서버 대기·캐시·요청 순서

**측정으로 확인:** 퀴즈타운 메인 첫 방문은 요청 시도 36개 중 정적 응답 35개, Auth 생성 시도 1개 차단이었다. 3회 모두 같은 구조이며 리다이렉트는 0회였다. 이 정적 응답들에서는 실패·일반적인 중복 URL 요청을 관찰하지 않았다. 독립 게임의 차단 오류는 아래 별도 범위다.

데스크톱 첫 방문의 DNS는 62–96ms, 연결 수립은 20–36ms(TLS 포함), TLS 부분은 12–29ms였다. 요청 발송→첫 바이트는 105–393ms였다. TTFB는 이 연결·네트워크·응답 대기를 합한 시간이며 서버 내부 실행 시간으로 해석할 수 없다. 첫 표본 TTFB 513ms를 상시 서버 지연이나 Functions 콜드 스타트로 단정하지 않는다. 메인 문서는 Hosting 정적 파일이고 이 측정에서 Functions를 실행하지 않았다.

- HTML은 `no-cache, no-store, must-revalidate`; 매 재방문에 약 62.5KB를 다시 받았다.
- JS/CSS는 실제 응답 기준 `max-age=300, stale-while-revalidate=3600`, SDK는 약 1년, 배경은 1시간 캐시였다. 즉시 재방문에는 정적 응답 35개 중 34개가 전송량 0으로 재사용됐다. “캐시가 전혀 없다”는 설명은 틀리다.
- 그라운드 HTML은 원문 3,749B이고 메인 JS는 원문 약 6.83MB다. 응답은 `max-age=0, must-revalidate`였으며 재방문 JS/CSS에 304가 나타났다. 그라운드의 작은 진입 HTML과 재검증 결과가 이번 재방문 TTFB·전송량 차이에 함께 반영됐다. Hosting 사업자 차이만 분리한 실험은 아니다.
- 브라우저는 HTML 수신 중 CSS·SDK·번들을 함께 발견해 요청한다. `<script>`가 연달아 있다고 다운로드를 모두 직렬 실행한다고 판단하면 안 된다. 다만 일반 script 실행 순서와 stylesheet 대기는 남는다.
- 대표 제한 환경 초기 실험에서는 Google Fonts CSS가 약 1.06초, 앱 번들이 약 1.11초 걸렸고, LCP 후보가 제목→본문→`#login-view` 배경으로 바뀌었다. 배경 다운로드 완료가 최종 큰 화면 표시를 늦추는 직접적인 근거다.

### 현재 코디 카탈로그와 이미 반영된 개선

현재 운영 `dressing-room.js`는 `verified-top50-display.json`을 읽는다. 과거 보고서의 4.72MB `verified-top50.json`을 현재 초기 경로의 병목으로 재사용하지 않았다. 4개 **공개 JSON만** 동일 출처 진단 문서에서 읽고 파싱한 3회 측정은 602.6 / 407.9 / 414.3ms, 중앙값 **414.3ms**, 전송량 **135.6KB**였다(4Mbps·80ms·CPU 4배). 회원 조회·상품 이미지·DOM 렌더를 포함한 상점 사용 가능 시간은 아니다.

현재도 JSON `no-store`와 fetch `no-store`는 남지만, display 파일 전송은 약 42.1KB이고 구 카탈로그의 약 1.62MB 전송을 현재 문제로 주장할 수 없다. 회원 상태와 카탈로그 병렬 로드, 상점 iframe 재사용도 코드에서 확인했다. 10월 4일 수치와의 차이는 경로 자체가 바뀐 결과가 포함되므로 이번 진단에서 수행한 전후 개선 실험이라고 부르지 않는다.

교실 클라이언트의 부분 표시도 이미 있다. 현재 유스케이스를 네트워크 없는 합성 공급자로 실행했을 때 설정 30ms, 일반 데이터 30ms, 경제 데이터 600ms 조건에서 일반 데이터는 약 **63ms**에 부분 전달되고 전체 모델은 **633ms**에 끝났다. 이는 인위적 의존성 실험이며 실제 응답/DOM 페인트 시간이 아니다. 여전히 전체 조작 잠금 해제는 최종 모델 뒤에 있다.

### 후속 집중 진단: 관리자·교실·상점 진입

**이번 우선순위 정정의 기준은 사용자가 느린 구간으로 지정한 세 화면이다. 초기 로그인 LCP·배경·폰트 수치로 이 세 화면의 병목 순위를 확정하지 않는다.** 기존 공개 첫 방문 측정은 반복하지 않았다. 아래에서는 운영 코드 대조, 로컬 실제 렌더러 실험, 아직 없는 운영 시간을 구분한다.

#### 환경·버전·시점의 정의

- 같은 M2 Pro·Chrome 154, 격리 컨텍스트, 1440×1000, CPU 감속 없음. 로그인 복원이 끝났다는 합성 전제에서 시작했다. 설치·제품 변경 없이 실제 로컬 HTML/스타일과 관련 유스케이스·렌더러·컨트롤러를 사용했다.
- 모든 브라우저 요청은 로컬 파일 또는 합성 응답으로 처리했다. Firebase SDK·운영 인증·실학생 데이터는 사용하지 않았다. 미리보기와 외부 이미지 응답은 1px 합성 이미지여서 실제 이미지 디코딩·헤어 염색 처리의 무게도 재현하지 않는다. 이 방식은 실제 TLS·네트워크·서버·HTTP 캐시·오류 재시도를 재현하지 않는다. ‘재진입’은 **앱 메모리 캐시와 살아 있는 iframe 재사용**이지 HTTP 캐시 벤치마크가 아니다.
- 관리자 80명, 교실 22명 등은 합성 규모다. 실제 반 인원·실제 기록량을 뜻하지 않는다. 상점은 현재 공개 카탈로그를 로컬 파일로 읽었으며 초기 표시 상품은 49개였다. 무인 실험의 입력 대기 시간은 사람의 숙련도나 운영 사용 시간으로 해석하지 않는다.
- 첫 진입 → 같은 화면 재진입 → 셸 화면 세 차례 왕복 후 재진입을 각 3회 실시했다. 왕복은 다른 뷰의 표시/숨김만 실행하며 다른 화면의 데이터 로더·presence·게임 세션은 실행하지 않았다. 따라서 장시간 실제 혼합 사용의 메모리 누수 검사는 아니다.
- 시간 시작점은 진입 함수를 호출하는 합성 버튼의 click 핸들러다. ‘표시’는 DOM 조건 후 두 번의 requestAnimationFrame을 거친 보수적인 관찰 시점이며, 실제 GPU 표시의 최초 순간이나 INP가 아니다. 뼈대/첫 반응은 같은 관찰 지점일 수 있다. 핵심 데이터는 관리자 대시보드와 회원 목록, 교실 포인트·코인·활동 모델, 상점 잔액·가격·보유 정보와 상품 목록이 준비된 상태다.

### 기타 확인과 미확정 가설

- **코드에서 확인:** `quiz-repository.js:716`의 메타 조회 후 `:724`의 `questions.orderBy('order').get()`는 해당 퀴즈의 전체 문항을 읽는다. 이후 메모리 캐시가 있다. 실제 문항 수·응답량을 읽지 않았으므로 현재 병목으로 확정하지 않는다. 전량을 받는 의미가 섞기·모드 선택과 관련 있으므로 무조건 limit를 추가하면 기능이 바뀔 수 있다.
- **코드에서 확인:** 메인 `startServerFreshnessPolling`과 `startTownSocial`은 타이머 중복 생성 방지가 있다. 따라서 화면 왕복마다 무제한 타이머가 쌓인다고 주장하지 않는다. 다만 로그인 상태이면 다른 내부 화면에서도 polling/heartbeat가 남을 수 있어 지속 사용 측정이 필요하다(`public/index.html:2864`, `:5407`).
- **코드에서 확인:** 내 방은 `requestAnimationFrame(drawRoom)` 루프와 20ms 아바타 타이머가 있고, 카탈로그를 유휴 시간에 순차 미리 처리한다(`housing/app.js:1055`, `:1353`, `:1544`, `:3499`). 잠금 화면에서 이 게임 루프의 실제 비용은 측정하지 못했다. 별도 문서 이동은 보통 문서를 종료하므로 메인 화면 뒤에서 모든 게임이 계속 돈다고 추정하지 않는다.
- **코드에서 확인:** 하우징 가구 묶음은 버전별 IndexedDB 캐시가 있다(`housing/assets-loader.js:13`). 코인 listener 해제 핸들을 보관하지 않는 코드가 있지만 초기화는 문서당 한 번이다. 반복 구독 누적은 재현하지 못했다. React 마블의 게임 세션에는 `leave()`에서 unsubscribe가 있다(`marble-src/src/online.js:333`). 소스는 원본에서 확인했고 빌드 산출물은 수정하지 않았다.
- **추가 검증이 필요한 가설:** 교실 전체 섹션 렌더·목록 교체와 코디 목록 재렌더가 저사양 기기에서 긴 작업을 만들 수 있다. 진단 중 교실 렌더러가 바뀌었고 실데이터 렌더 trace가 없어 현재 CPU 병목으로 확정하지 않았다. 필요 없는 화면의 DOM을 만들지 않는 개선은 데이터 공급 개선과 별도 검증해야 한다.
- **추가 검증이 필요한 가설:** Functions 콜드 스타트·DB 리전·쿼터·Storage 다운로드 지연. 클라이언트 `public/js/core/firebase.js:33`과 서버 `functions/index.js:15`의 함수 리전 선언은 모두 `asia-northeast3`이다. 실제 Firestore/Storage 위치, 운영 minInstances, 비용·쿼터·서버 로그는 확인하지 않았다.

**수정 권고:** 프런트엔드에서 관리자 불필요 호출을 줄이는 1번과, 관리자·교실의 조회/캐시 구조를 다루는 2번을 우선 결합한다. 배경·글꼴부터 고쳐야 한다는 순서는 철회한다. 3번 이전의 필요성·기대 성능은 운영 증거 부족으로 유보한다. 전체 React 전환이나 백엔드 이전이 성능 개선의 선행 조건은 아니다. 큰 파일·불필요한 초기 작업을 줄이고, 클릭에 즉시 피드백을 주고, 데이터 준비 시점을 분리하는 원칙은 현재 코드에서도 적용할 수 있다.

Firebase Hosting은 정적 콘텐츠를 CDN에 캐시하며 응답 캐시 정책을 조정할 수 있다. 현재 서비스 선택 때문에 캐시 개선이 막혀 있는 것은 아니다. 다만 학생별 동적 응답을 공개 CDN 캐시로 돌리는 제안은 하지 않는다. [Firebase Hosting 캐시 공식 문서](https://firebase.google.com/docs/hosting/manage-cache).

2026-10-07 후속 진단에서도 공식 문서를 다시 확인했다. Firestore 공식 지침은 사용자/컴퓨트와 데이터 위치, 불필요한 읽기, 독립 작업의 비동기 실행을 지연 요인으로 다룬다. 이는 현재 조회 의존성을 먼저 줄여야 한다는 권고와 부합한다. 이번에는 운영 DB 위치를 확인하지 않았으므로 지역 이전 효과를 숫자로 제시하지 않는다. [Firestore 성능 지침](https://firebase.google.com/docs/firestore/best-practices).

Functions 최소 인스턴스는 콜드 스타트 완화 수단이지만 유휴 비용이 있고 설정 범위를 넘는 확장에서는 최초 실행이 생길 수 있다. 운영 설정·실제 최초/반복 호출 차이를 확인하기 전에 켜지 않는다. 요금 액수·현 서비스 비용·절감액은 추정하지 않았다. [Functions 인스턴스·확장 공식 문서](https://firebase.google.com/docs/functions/manage-functions#control_scaling_behavior).

### 이전을 검토할 구체적인 조건

1. 리소스·중복 조회·권한 확인 이후 독립 읽기 최적화를 마쳤는데도, 동일 지역의 인증된 읽기 경로에서 **서버 구간이 반복적으로 전체 대기의 대부분**임을 trace로 확인한다.
2. 학교의 실제 동시 이용 규모에서 목표 지연을 정하고, 최초 호출/반복 호출·혼잡 시간·오류를 구분한 다일 측정에서 현 구조가 목표를 지속적으로 못 맞춘다. 이번 3회 공개 측정으로 판단하지 않는다.
3. 확인된 원인이 Firestore 쿼리/집계 모델, 사용 가능한 지역, 실측 비용 등이고 Firebase 내 재설계보다 다른 서비스가 유리하다는 근거가 있다. 대안의 공식 제한·비용도 그 시점에 확인한다.
4. 익명화 합성 데이터로 작은 **읽기 전용 경로**를 같은 화면·같은 응답 데이터량·같은 네트워크에서 비교해 재현 가능한 개선을 보인다. 공급자 이름만 바꾼 비교는 충분하지 않다.
5. 전면 이전 전 인증 연결·규칙·랭킹·보상/구매의 무중복·데이터 대조·롤백을 구체화하고 사용자 승인을 받는다. 외부 서비스 선택과 운영 데이터 이동은 이번 진단 범위 밖이다.

## 7. 추가 확인이 필요한 사항

### 가장 먼저 수행할 개선 3개

1. **관리자 진입 작업 분리.** 최고 관리자의 운영/퀴즈 점검을 명시적 실행으로 옮기고, 대시보드에 필요한 데이터만 먼저 받는다. 회원 목록 재사용과 대시보드 독립 조회 병렬화를 함께 검토한다. 실제 운영 호출 10→2를 목표로 삼을 수 있지만, 데이터 대기 80% 감소로 환산하지 않는다. 반 관리자라면 기본 대시보드 쿼리 개선부터다.
2. **교실 핵심 데이터와 조작 잠금 범위 분리.** today에 필요한 값부터 완료·활성화하고, 학생카드/마켓/은행은 필요 시 로드한다. 카드 레벨 N+1을 권한 검증 응답에 합치는 방안을 검증한다. 잔액·가격 미확정 상태의 거래는 계속 잠근다.
3. **상점 클릭 반응과 실제 준비 단계를 분리.** flags 확인 중 즉시 셸을 표시하고, 상품/잔액/미리보기 각각 준비 상태를 알린다. status·카탈로그의 기존 병렬화와 iframe 재사용을 보존한다. preview 자체의 대기는 최소 권한 조회/캐시와 외부 렌더 실측을 근거로 줄인다. 교실 마켓을 지목한 경우 2번에 포함한다.

### 개선 전후를 비교하는 고정 절차

- 이 보고서의 운영 SHA와 개선 후보 SHA를 각각 고정하고, 같은 Chrome 버전·기기·화면 크기·네트워크 설정에서 A/B 순서를 번갈아 실행한다. 두 버전은 동일한 합성 데이터와 권한을 사용한다. 운영 학생 데이터로 반복 벤치마크하지 않는다.
- 세 화면은 역할·인원·카탈로그·최초 성별 선택 여부를 고정하고, 로그인 복원 후 최초 진입/재진입/혼합 화면 왕복을 각 3회 비교한다. 실제 클릭 시각과 서버/데이터/DOM/조작 해제/preview 완료를 따로 기록한다. 운영에서는 일반 사용자 방문 수준을 넘지 않는다. 공개 첫 화면 비교가 필요할 때만 격리 cold와 같은 컨텍스트 warm를 나눈다. 모바일은 이번 최종 결과처럼 load 후 12초를 기본 관찰하고 미완료 요청이 있으면 **양쪽** 관찰창을 늘린다. 중앙값·범위·실패·미완료 요청을 함께 남긴다.
- 첫 화면: TTFB/FCP/LCP/CLS, 응답·전송 바이트, 글꼴/이미지/JS 분해, 긴 작업을 비교한다. Lighthouse 점수만으로 성공 판정하지 않는다.
- 내부 전환: `click → 최초 시각 피드백 → 필수 데이터 수신 → 필수 렌더 완료 → 조작 잠금 해제`를 각각 기록한다. “100ms 안에 최초 피드백”은 제안하는 목표이지 현재 모든 화면의 달성치가 아니다.
- 인증: SDK 초기화/인증 상태 확정/회원 복원/목적 화면을 따로 계측하고, 중복 요청·오래된 계정 응답·캐시 무효화 횟수를 함께 검증한다. SDK 다운로드 시간과 로그인 완료 시간을 섞지 않는다.
- 쿼리 개선: 학생 수·랭킹 행·문항 수·카탈로그 버전을 고정한다. 공급자 호출 수와 실제 HTTP 요청 수, 반환 문서/바이트, 서버 실행 시간을 별도 기록한다. 합성 “22명” 수치를 운영 학급 규모로 간주하지 않는다.
- 실제 사용자 INP는 별도의 최소수집 실사용 계측이 필요하다. 학생 이름·ID·토큰·답안·URL의 개인별 매개변수는 보내지 않고 집계 시간만 수집하는 설계를 먼저 검토한다.
- 제품 개선 후에는 AGENTS.md의 `npm run check`와 대상별 회귀 검사를 수행한 다음 별도 배포 검토를 한다. **이번 단계에서는 `npm run check`를 실행하지 않았다.** 빌드가 제품 번들을 재생성하고 진단 중인 작업 트리를 바꿀 수 있으며, 제품 수정 없는 진단 범위였기 때문이다.

### 아직 필요한 운영 증거

- 그라운드의 로그인 후 정확한 대응 화면·권한·데이터량. 퀴즈타운의 집중 구간은 이제 관리자/교실/상점으로 확정했다. 관리자 권한 등급과 상점이 코디인지 교실 마켓인지는 사용자 확인 질문을 남겼으며 두 경로를 모두 분석했다. 현재 공개 소개 화면 비교만으로 대시보드 차이를 설명할 수 없다.
- 자동 presence·쿠폰·조회 부수 쓰기를 통제할 수 있는 테스트 계정/테스트 프로젝트와 허용 범위. 먼저 운영 쓰기 없이 재현 가능한 환경에서 인증 이후 계측을 진행한다.
- 실제 배포 Functions 리비전·리전·min/maxInstances·동시성, Firestore/Storage 실제 위치, 인증된 읽기 함수의 서버 trace, 쿼리 실패/재시도 집계. 권한 있는 읽기 자료에서 민감값을 제외하고 확인해야 한다.
- 실제 학생 단말의 CPU·메모리·학교 Wi‑Fi 조건, 긴 세션의 구독/타이머/힙 변화, 내 방 가구 수와 게임 중 프레임·입력 지연.
- 수학서바이버의 CLS 변동 원인, 교실 전 탭 렌더 비용, 퀴즈 문항 응답 크기. 확인 전에는 큰 문제라고 추정해 수정하지 않는다.

### 후속 운영 실측의 최소 절차와 사용자 확인 항목

현재 열린 인증 세션이 없어 이 단계는 실행하지 않았다. **사용자의 운영 쓰기 금지 지시와 AGENTS.md의 학생 데이터/운영 설정 변경 승인 기준** 때문에 로그인·부수 쓰기를 임의 실행할 수 없다. 코드 읽기와 위 합성 측정은 완료했다.

| 단계 | 최소 실행·수집 | 예상 쓰기/제약 | 사용자 확인 |
| --- | --- | --- | --- |
| A. 기존 인증된 진단용 세션 | 이미 열린 테스트 계정 탭을 사용, 토큰/쿠키/본문/화면 개인정보 저장 없이 함수명·상태·ms·반환 바이트만 수집 | 기존 세션을 복사하지 않음. 활성 인기 퀴즈가 없고 town heartbeat가 멈춰 있는지 먼저 확인. 이를 보장 못 하면 운영 화면 전체 진입을 실행하지 않음 | 사용할 세션·권한·관리자 등급 확인. 이 경로 자체에 새 로그인 승인을 요구하지 않음 |
| B. 읽기 경로만 1회 예비 측정 | 관리자 dashboard/members, 상점 status/preview를 allowlist로 허용. adminGetFeatureFlags·자동 두 audit·presence·게임 쓰기·구매/장착/염색 차단. 이후 필요하면 같은 read-only 흐름 2회 추가 | 요청 차단 때문에 정상 전체 진입과 타이밍이 달라짐. 부분 경로의 실제 서버 시간만 보고. 관리자 기본 조회도 최대1,000 rows 등 범위를 먼저 확인하며 무분별한 반복 금지. preview는 외부 렌더 컴퓨팅 이용 | 기존 세션·허용 경로가 준비되면 읽기 진단은 이미 요청 범위. 세션 제공과 데이터량 적합성 확인 필요 |
| C. 세션이 없어 전용 계정으로 새 로그인 | 사용자가 직접 정상 로그인 1회. 임시비밀번호 발급/재설정·신규 계정 생성은 안 함 | `loginMemberWithPassword`의 credentials.lastLoginAt/updatedAt, users/authLinks 연결 및 로그인 로그가 변경될 수 있음. 격리 신규 익명 Auth가 필요하면 Auth 사용자 생성도 생김 | **전용 테스트 계정의 이 로그인 부수 쓰기를 허용할지 명시적 확인 필요. 승인 전 실행 안 함** |
| D. 교실 경제 실제 서버 구간 | 기존 진단 계정으로 첫 진입 1회. settings·학생카드·지갑 등 읽기와 economy 구간을 분리 계측 | 경제 조회는 학급 공용 미션 달성일을 조건부 저장. 테스트 학생이어도 학급 공용 문서에 영향 가능. 차단/모의하면 이 함수의 운영 지연은 측정 불가 | **미션 달성일 쓰기를 별도 허용하지 않으면 운영 economy 호출 보류. 테스트 프로젝트의 합성 학급으로 대체** |

확인 요청은 **C의 전용 계정 정상 로그인 1회 허용 여부 및 A의 기존 진단용 세션 제공 가능 여부**다. D의 학급 공용 쓰기는 묶어서 승인받지 않는다. 실제 서버 병목 판별에는 권한 있는 읽기 자료로 함수 진입/권한 완료/Firestore 완료/직렬화 완료의 trace가 필요하다. 요청 발송→응답 시간만으로 Firestore와 콜드 스타트를 구분할 수 없다. 새 운영 계측 코드나 로그 배포는 별도 작업이다.
