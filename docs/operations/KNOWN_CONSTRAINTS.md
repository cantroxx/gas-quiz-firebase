# Known Constraints

## 목적

운영 중 확인된 제약사항과 정책 결정을 고정해, 이후 작업에서 같은 버그를 다시 만들거나 정책을 흔들지 않도록 한다.

기준일: 2026-07-08

## 1. users 컬렉션에 orderBy("userId") 사용 금지

- 2026-07-08 이전에 신규가입으로 만들어진 users 문서에는 `userId` 필드가 없다.
  - 원인: `registerNewMember`가 문서 ID만 userId로 쓰고 필드는 저장하지 않았다. f482991에서 수정되어 이후 가입 계정은 필드를 가진다.
  - 기존 계정 백필은 하지 않았다(사용자 결정). 따라서 구계정 문서에는 필드가 계속 없다.
- Firestore의 `orderBy`는 정렬 필드가 없는 문서를 결과에서 제외한다. 이 정렬을 쓰면 구계정이 조회에서 통째로 빠진다.
  - 실제 발생 사례: 슈퍼관리자 회원 목록에서 테스트 계정(G5-C5-N55)이 조회되지 않는 버그.
- 정렬이 필요하면 문서 ID 기본 정렬을 사용한다. users 문서 ID가 곧 userId라 정렬 결과는 같다.
- 관련 커밋: bc4f3e1(adminListMembers), 1d28eee(adminGetDashboard·adminListStudentEconomy), ffda39a(가입 시 userId 저장) — 2026-07-08 이력 재작성(filter-repo) 이후 해시 기준

## 2. 숨김 학생 노출 정책

숨김 학생(예: G4-C8-N23, `HIDDEN_CLASSROOM_MEMBER_IDS`)은 활동은 하되 화면 노출만 막는 테스트 계정이다. 표시 위치에 따라 기준이 다르다.

- 처리용 카운터·목록(처리할 일, 쿠폰 요청 등): 숨김 학생을 **포함**한다. 교사가 처리해야 하는 대상이므로 카운터와 처리 목록의 건수가 항상 일치해야 한다.
- 노출성 표시(최근 교실 활동 피드, 공개 랭킹, 학생에게 보이는 학생카드): 숨김을 **유지**한다.
- 새 집계나 목록을 추가할 때는 위 두 분류 중 어디에 속하는지 먼저 정하고 필터 적용 여부를 결정한다.
- 관련 커밋: 3c5f4f4(처리할 일 카운터), f9d3976(쿠폰 요청 카운터)

## 3. 상점 두 종류와 승인 흐름 구분

상점이 두 곳이고 구매 후 흐름이 다르다. 혼동하면 승인 UI를 엉뚱한 곳에서 찾게 된다.

- 마을 상점(DJ48 상점, 상점 진열대): 즉시 사용 아이템. 구매 즉시 적용되고 교사 승인 흐름이 없다.
  - 2026-07-08 더미 계정으로 구매 동작 확인 완료.
- 교실 마켓(우리 교실 > 마켓 탭, 포인트샵·코인샵)의 쿠폰형 상품: 승인 흐름이 있다.
  - 상태 전이: 구매(purchased) → 학생 사용 요청(use_requested) → 교사 승인(use_approved) → 사용 완료(used). 반려(use_rejected)는 요청·승인 상태에서 가능하다.
  - 교사 승인 UI 위치: 교실 화면 마켓 탭 > 인벤토리("인벤토리 사용 요청" 테이블). 관련 커밋: 2596118(최초 구현), bbd03ed(요청 시각 열 추가).
- ⚠️ 승인→완료 실동작은 아직 테스트하지 않았다. 실제 쿠폰 사용 요청이 처음 발생할 때 교사가 승인·완료 처리가 정상 동작하는지 확인해야 한다.
