## 1. 결과와 확인 범위

현재 과목 퀴즈는 생성형 단원 퀴즈이고, 인기 퀴즈는 국기·아이돌·애니·티니핑·포켓몬 5개 분야다. `quiz-catalog.js`만 보면 과거 목록이 남아 있으므로 잘못 판단하기 쉽다. 실제 빌드 순서대로 `subject-quiz-catalog.js`, `popular-quiz-catalog.js`까지 실행해 최종 목록을 확인했다. 과목 카드 수는 국어 3, 수학 2, 사회 3, 과학 2이며 각 카드에서 단원을 선택한다.

확인한 주요 낭비는 다음과 같다.

| 순서 | 항목 | 근거 수준 | 권장 처리 |
| --- | --- | --- | --- |
| 1 | 개인·단일 과목 랭킹에 전체 과목/회원 집계 조회 사용 | 공개 운영 프런트 확인 + 로컬 서비스 합성 재현 | 목적별 조회 API로 분리 |

이번에 운영 소스·데이터·Rules·인덱스를 바꾸지 않았다. 배포·commit·push·학생 로그인·운영 callable 실행도 하지 않았다. 새 파일은 이 보고서, 재실행 가능한 오프라인 감사 스크립트, JSON 증빙이다. `private/`, `exports/`, 루트 Apps Script 파일은 열지 않았다.

**한계:** 운영 Firestore 문서 수·실제 비용·요청량·지연·Cloud Functions 배포 소스·TTL 설정·외부 클라이언트 호출 로그는 조회하지 않았다. 따라서 “서버 과부하가 발생했다”거나 “운영 데이터 N건을 안전하게 삭제할 수 있다”는 결론은 내리지 않는다. 아래 읽기/쓰기 수는 코드와 합성 재현 결과이며 실제 청구량이 아니다.

## 3. 먼저 줄일 조회·쓰기

### R-01. 개인 랭킹이 전체 회원 랭킹을 읽는다 — 높음

- `public/js/infrastructure/ranking-repository.js:308`: 본인의 `rankingRecords`를 최대 500건 읽은 다음 `loadSubjectRankingSnapshot()`을 호출한다. 받아온 전체 과목 기록을 브라우저에서 본인 것으로 필터링한다.
- `functions/subject-quiz/service.js:46`: `rankingSnapshot`은 4개 과목 랭킹 컬렉션을 각각 최대 501건, `quizKingSummary`를 최대 501건 읽는다. 이 전에 인증 연결·회원·기능 설정·세션 제어 문서 4개도 읽는다.
- `public/js/application/ranking-usecases.js:9`: 퀴즈왕뿐 아니라 국어·수학·사회·과학 중 한 분야를 열어도 같은 전체 스냅샷을 사용한다. 상위 10개 제한은 서버 조회 후 적용된다.

각 집계에 합성 회원 30명씩 넣은 재현에서 문서 154개를 반환하는 읽기 구조, 과목 행 120개를 확인했다. 개인 랭킹 저장소 함수를 두 번 호출하면 전체 스냅샷도 두 번 호출된다. 저장소 함수 자체에 공유 캐시는 없다. 다만 홈 상세 패널에는 30초 캐시가 있으므로 클릭마다 무조건 호출된다고 해석하면 안 된다.

각 컬렉션에 500건씩 있으면 단일 시도에서 집계 문서만 2,500건이다. 501건을 발견하면 이미 읽은 후 오류를 반환한다. 실제 데이터 수·트랜잭션 재시도에 따른 부하는 미측정이다.

**수정 방향:** 개인 기록은 본인 과목 문서 4개만, 과목 게시판은 해당 과목 정렬·상위 N개만, 퀴즈왕은 별도 집계만 가져오도록 분리한다. 회원/권한별 요청 병합과 짧은 캐시를 적용하고 점수 갱신·로그아웃 시 무효화한다. 현재 `board` 액션도 있으나 UI에 필요한 필드/순위 규칙을 맞춰야 하므로 단순 교체하지 않는다. `rankingRecords`·`userRankingSummary`·`quizKingSummary`를 지워서 해결하지 않는다.

**통과 조건:** 본인 기록 조회에 타 회원 컬렉션 스캔 0회, 단일 과목 화면에서 다른 과목/퀴즈왕 조회 0회, 동점·비공개 회원·최고 기록·종합 랭킹 의미 유지, 계정 전환 시 캐시 격리.

### R-03. 폐지된 인기 이용시간 정책용 데이터가 새 과목에서 갱신된다 — 중간

`functions/index.js:9381`의 `rewardGeneratedSubjectAnswer()`는 정답 처리에서 `dailyUsage`를 읽고 `eduCorrectCount`와 `unlockBaseEduCorrectCount`를 다시 쓴다. 연습 보상 여부와 별도로 수행하므로 랭킹 정답도 해당된다.

현재 `/popular-quiz/` 서비스는 시간 제한 대신 한 판 20문제 규칙을 사용하며 이 사용량 문서를 조회하지 않는다. 반면 구형 `getPopularQuizUsageStatus`, `recordPopularQuizUsageSeconds`, `recordEducationCorrectForPopularUnlock`, 일반 퀴즈 저장소의 관련 경로와 관리자 감사는 남아 있다. 따라서 `dailyUsage` 전체 삭제를 안전하다고 판단하지 않는다.

**수정 방향:** 새 인기 화면으로의 전환과 구형 세션/외부 호출 종료를 확인한 뒤, 새 과목 정답 경로의 `dailyUsage` 읽기 1회·쓰기 1회를 중단한다. 기존 시간 제한 API의 종료 응답과 보관 정책은 별도로 정한다. 인증·보상 한도 문서는 삭제/캐시 완화 대상이 아니다.

### R-04. 종료된 시즌 문서를 매분 감시한다 — 중간, 작은 변경으로 개선 가능

`public/index.html:2810`은 로그인 회원에 대해 첫 2.5초 뒤, 이후 60초 간격으로 설정 변경을 확인한다. `public/js/infrastructure/admin-repository.js:82`는 매번 다음 4개 문서를 가져온다.

`appSettings/featureFlags`, `appSettings/externalQuizzes`, **`appSettings/seasonEvents`**, `noticeBoard/current`.

종료된 시즌 문서가 실제 조회 목록에 들어가는 것을 합성 재현했다. 소스에는 페이지 가시성 검사나 체크 요청 중복 병합이 없다. 다만 브라우저의 백그라운드 타이머 지연과 SDK 캐시 때문에 실제 서버 읽기는 코드상의 호출 횟수와 다를 수 있다.

시즌 문서 1개만 제외해도 이 점검의 문서 get 호출 수는 4→3이다. 예를 들어 로그인 창 30개에서 40분간 매분 정상 실행한다면 시즌 관련 get은 1,200회 규모이며 초기 체크/수동 새로고침은 별도다. 이는 청구량 예측이 아닌 호출 모델이다.

**통과 조건:** 설정·공지 변경 알림 유지, 시즌 get 0회, 로그아웃·숨김 상태 처리, 재진입 시 갱신, 중복 요청 병합.

### R-05. 관리자 문제 점검의 범위가 개편 전 문제은행이다 — 중간

`functions/index.js:4190`의 `adminGetQuizQualityAudit`는 `quizzes` 최대 300개를 읽고 각 퀴즈의 문제를 최대 1,200개씩 가져온다. 단순 코드상 상한은 문제 360,000건이지만 실제 문항 수는 확인하지 않았다. 제외 대상은 `science-grade4` 한 ID뿐이다. 현재 단원 생성기와 인기 아이돌·애니 정적 팩은 이 점검으로 직접 검사되지 않는다.

현재 관리자 첫 진입은 대시보드만 읽도록 이미 개선되어 있다(`admin-usecases.js:58`). 이 무거운 점검이 매 로그인에 자동 실행된다고 보지 않는다. 별도 섹션/버튼에서 호출되는 점검의 비용과 범위가 문제다.

**수정 방향:** 현재 서비스가 쓰는 문제은행과 보관된 문제은행을 분리해 선택적으로 검사한다. 생성형/정적 문제는 로컬 검사 결과를 사용하고, Firestore 검사는 분야별 제한·페이지·결과 캐시를 둔다. 부하를 알아보려고 이 운영 감사를 무작정 실행하지 않는다.

## 4. 정적 파일: 중복 삭제보다 이미지 경량화의 효과가 크다

오프라인 스캔 결과(`node_modules`, 숨김 파일, `dev-assets` 제외): `public/` 4,769파일, 578,810,053바이트. 완전히 같은 바이트의 중복은 97그룹, 사본을 하나씩만 남긴다는 가정의 중복량은 5,309,061바이트다. 이는 **삭제 가능 용량이 아니라 중복 바이트 총량**이다.

- 가장 큰 동일 사본: `public/images/town-storybook-plazas-v2.png`와 `public/town-preview/assets/village-b-plazas-v2.png`, 약 3.23MB. 독립 미리보기 경로를 쓰는지 확인하고 참조를 통합해야 한다.
- 코디 이미지에는 서로 다른 아이템 ID인데 바이트가 같은 파일이 있다. 데이터 키와 URL 계약 때문에 해시만 보고 지우면 안 된다.
- 메달 `candidates/`와 `levels/`의 사본은 후보 보관/운영 사용을 구분해야 한다. 파일명에 candidate가 있다고 곧바로 삭제하지 않는다.
- 소스와 `app.bundle.js`, React 소스와 빌드 출력, 서버/클라이언트 문제 생성 코드의 복제는 생성 관계가 있는 산출물이다. 필요 없는 사본으로 분류하지 않는다.

**인기 이미지가 더 큰 개선 대상이다.** 현재 로컬 팩 551문항은 이미지 551개를 모두 참조하고 누락/미참조 파일은 0개다. 합계 385,232,240바이트(약 385MB), 1MB 초과 66개, 최대 13,485,055바이트다. `public/popular-quiz/app.js:50`은 전달받은 `q.imageUrl`을 그대로 `img.src`에 사용한다. 이 이미지는 쓰이는 데이터이므로 삭제 대상이 아니다.

썸네일/퀴즈 표시 크기에 맞춘 WebP 등 파생본을 만들고 얼굴·그룹 구분, 정답 식별성, 출처 원본/해시를 보존하는 것이 우선이다. 새 문제만 파생 URL을 사용하게 전환한 뒤 기존 진행 중 `popularQuizRuns.questions[].imageUrl` 참조가 끝날 때까지 원본 URL을 유지해야 한다. 전체 이미지 용량이 한 번의 방문에서 모두 전송된다는 뜻은 아니다. 이번에는 운영 이미지 다운로드나 가공을 하지 않았다.

`firestore.indexes.json`의 `fieldOverrides`는 비어 있고, 조사한 새 세션/문항 경로에 자동 정리 작업은 확인되지 않았다. **운영 콘솔 TTL이 없다는 증거는 아니다.** 로컬의 `deadline`/숫자형 `issuedAt`이 있다고 자동 삭제되는 것도 아니다. 학생 데이터 보존 기한을 임의로 7일/30일 등으로 정하지 않는다.

세션/활동 원장을 먼저 지우면 동일 요청 재시도 때 보상이나 집계를 다시 수행할 수 있다. 부모 문서만 정리하고 하위 컬렉션을 남기는 방식도 불완전하다. 삭제 명세는 전체 경로, 버전, 종료 상태, 최근 수정 시각, 참조 여부, 하위 컬렉션을 포함해야 한다.

## 7. 실행 순서와 완료 기준

1. **운영 기준 고정:** 최신 Hosting/Functions 소스와 현재 수정 범위를 대조하고 백업한다. 다른 작업의 변경을 섞지 않는다.
2. **데이터를 지우지 않는 조회 최적화:** R-04 폴링, R-01 랭킹 조회 분리, R-05 관리자 검사 범위. 합성 요청 수/반환량과 화면 동작을 검증한다.
3. **구형 쓰기 중단:** R-02/R-03의 보상·한도·새 퀘스트 보존 검증을 준비하고 학생 데이터 영향 변경 승인을 받는다.
4. **함수/정적 파일 정리:** 헬퍼 및 시즌 UI를 기능별로 제거한다. 이미지 파생본을 생성하고 기존 세션 URL을 보존한다. 빌드 산출물을 직접 수정하지 않는다.
5. **운영 읽기 전용 후속 조사:** 함수별 호출량/지연/오류, 스케줄·TTL, 컬렉션별 count/최신 갱신/버전 분포를 필요한 범위만 집계한다. 무제한 문항/학생 문서 조회를 점검 수단으로 쓰지 않는다.
6. **데이터 정리 실행 명세:** ID/경로별 후보 목록·제외 목록·원본 백업·복원 검증·버전 조건·작은 배치·중단 기준을 만든 뒤 승인을 받는다. 변경 후 대상이 갱신되면 해당 배치에서 제외한다. 제거 후 새 서비스/구형 호환 응답·재지급 방지·진행 중 게임 복구를 검증한다.

보안 규칙·인덱스 삭제는 데이터 삭제의 자동 후속 단계가 아니다. 아직 쓰는 조회·외부 서비스·구형 클라이언트를 확인하고 별도로 처리한다.
