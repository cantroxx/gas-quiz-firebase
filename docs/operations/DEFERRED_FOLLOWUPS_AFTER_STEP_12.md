## 목적

1~12단계에서 확인된 보류점을 잊지 않고 한 번에 보완한다. 2026-09-02에 로드맵 9~12단계까지 완료했으므로, 이제 이 문서가 다음 작업의 단일 관리 목록이다.

보류는 해결 완료를 뜻하지 않는다. 보완 작업 중에도 아래 금지선을 지키며 읽기 전용 확인과 안전한 로컬 코드·콘텐츠·문서 작업만 할 수 있다. 개인정보·회원·학생 데이터 삭제, 대량 데이터 변경, Firebase 규칙 배포, 유료 에셋 공개, 원격 push와 운영 deploy는 각 항목의 승인 게이트를 통과하기 전 실행하지 않는다.

## 진행 규칙

1. 완료된 로드맵 1~12단계의 로컬 변경을 보존한다.
2. 이 문서의 `D-01`부터 순서대로 현재 상태를 다시 확인한다.
3. 데이터·공개 범위·운영 설정은 승인 전 바꾸지 않고 읽기 전용 확인과 안전한 로컬 문서 보완부터 한다.
4. 읽기 전용 확인과 dry-run을 먼저 하고, 삭제·이동·마이그레이션·규칙 배포·원격 공개는 사용자에게 대상과 영향을 설명한 뒤 승인받는다.
5. 항목별 결과는 `미확인` / `확인 완료` / `사용자 결정 필요` / `보완 중` / `완료` / `유지 보류`로 기록한다.
6. 한 항목의 해결을 위해 다른 프로젝트의 파일이나 운영 데이터를 함께 정리하지 않는다.

- 9단계 `battle-school`: 위 보류 항목과 분리해 로컬 싱글플레이 깊이와 회귀 검증을 완료했다.
- 10단계 `kbo-owner`: `D-06`의 공개·실명 금지선을 유지하면서 엔진·역할·계약·시즌 시스템을 개발했다.
- 11단계 `life-diary`: 출처 문제 없는 코드 기반 장면과 생성 기록 문서를 사용했다. 원격·Vercel 연결은 `D-02`, 전용 이미지는 `D-09`로 남겼다.
- 12단계 문서 정리: 각 README에 현재 제한을 사실대로 적고, 확인되지 않은 배포 연결은 `D-12`로 남겼다.

## 12단계 이후 일괄 처리 순서

1. 모든 저장소의 작업 트리·브랜치·원격·최근 커밋을 읽기 전용으로 다시 조사한다.
2. 유일 원본과 운영 의존 파일의 백업 계획을 먼저 세운다.
3. `D-01`~`D-12`의 사용자 결정이 필요한 선택지를 영향도와 함께 제시한다.
4. 승인 없이 가능한 문서·ignore·검사 보완부터 처리한다.
5. Firebase·학생 데이터·에셋 이력처럼 되돌리기 어려운 작업은 dry-run·백업·복구 절차를 검증한 뒤 별도 승인으로 실행한다.
6. 전체 빌드·린트·브라우저 smoke와 운영 경계 검사를 다시 수행하고 결과를 이 문서와 로드맵에 기록한다.

## 완료 조건

- `D-01`~`D-12`가 모두 `완료` 또는 사용자가 선택한 `유지 보류` 상태다.
- 공개 저장소와 배포본에 비밀값·무단 유료 에셋이 새로 포함되지 않았다.
- 학생·회원 데이터 관련 변경은 백업·최소수집·권한 검증과 사용자 승인을 거쳤다.
- 원격 백업·배포 관계와 라이선스·출처가 프로젝트 README에 반영됐다.
- 삭제·이동·마이그레이션이 있었다면 대상, 복구 방법, 검증 결과가 남아 있다.
