큰 파스텔 카드가 퀘스트의 얇은 구분선과 마켓의 중립색 상품 면으로 바뀌었다. 녹색은 선택 위치와 주요 행동에 집중된다. 같은 높이에서 더 많은 활동과 상품 정보를 볼 수 있다.

탭은 시각적 무게와 중복 제목을 줄였지만 **마켓의 상위 메뉴 → 마켓/은행 → 상품 분류 3단계는 그대로다.** 탐색 깊이가 줄었다고 평가하지 않는다. 모바일 교사 화면도 메뉴·등록·검토·필터를 갖추기 때문에 첫 활동까지 398px를 사용한다. 이를 더 줄이는 것은 탐색 구조를 별도로 다루는 후속 과제다.

이번에 확인하고 추가 보완한 항목:

1. 모바일 교사 필터가 항상 펼쳐져 첫 활동을 밀어냈다. 기본은 접고, 적용 중인 필터 개수를 표시한다. 필터를 바꾸면 펼침 상태와 입력 포커스를 유지한다. 데스크톱은 계속 펼쳐 보인다.
2. 모바일 상품 이미지의 80px 규칙이 더 강한 CSS에 밀려 96px로 남아 있었다. 우선순위를 바로잡았다.
3. 이미지 내부의 백분율 크기가 그리드에서 104px로 계산되어 작은 이미지 칸에서 일부 잘렸다. 그림 자체를 데스크톱 96×96, 모바일 80×80로 명시해 잘림을 없앴다.

모바일에서 간식 상품 선택 직후 학생 구매 버튼과 교사 수정 버튼은 모두 844px 화면 안에 들어왔다. 개편 전에는 상세가 목록 끝에 있고 자동 이동이 없어 두 버튼 모두 화면 밖에 있었다. 실제 클릭 후 스크롤 위치를 유지한 캡처로 확인했다.

## 생성 그림의 실제 크기 평가

[실제 크기 비교판](../product/classroom-final-review-2026-10-07/pairs/assets-actual-size.png)은 확대하지 않은 요소 캡처다. 생성 그림을 새로 만들거나 원본을 다시 편집하지 않고, 실제 적용 크기와 잘림을 확인했다.

- 간식/급식 그림: 모바일 80×80px. 과자·음료와 식판의 실루엣을 구분할 수 있다. 식판 안의 반찬은 작은 색 덩어리로 읽히며 세부 질감은 의미 전달에 필수적이지 않다.
- 상품 카드 전체 248px 중 이미지 면은 80px다. 별도의 제목·가격·상태·44px 행동 영역을 확보한다. 큰 반복 이미지가 상세에 다시 나오지 않는다.
- 활동 노트: 모바일 40×40px. 노트 실루엣은 읽히지만 종이 세부 질감은 거의 보이지 않는다. 실제 제목과 해야 할 일이 의미를 전달한다.
- 빈 정리함: 88×88px. 보조 그림으로 작동하며 아래 안내 문구와 경쟁하지 않는다.
- 남은 시각적 차이: 생성 그림의 가는 종이 질감과 기존 SVG의 굵고 단순한 윤곽선은 완전히 같지 않다. 작은 크기에서 식별이 깨지는 문제는 없었으므로 이번 점검에서는 에셋 전체 재생성을 하지 않았다.

## 전체 재렌더 증가의 재현과 분리 실험

서버 호출을 차단한 Chromium, CPU 4배 제한, 1440×1000, 합성 학생 24명/퀘스트 12개/상품 60개를 유지했다. 다른 테스트를 동시에 실행하지 않았다. 변경 전/후 순서를 번갈아 실행해 항상 두 번째 실행이 유리하거나 불리해지는 영향을 줄였다. 각 값은 실행별 중앙값의 중앙값이다.

### 1. 재점검 시작 버전 8쌍

전체 재렌더: 34.25→36.30ms. 각 쌍의 차이는 −3.5~+7.5ms, 차이의 중앙값 +0.5ms였다. 실행 간 편차가 있어 이 단계만으로는 판단이 불충분했다. 참고용 짝별 평균 차이 bootstrap 95% 구간도 −0.76~+3.86ms로 0을 포함했다(8쌍으로 확정적 통계 결론을 내릴 수 없음).

### 2. 모바일 보완을 포함한 최종본 4쌍

| 항목 | 개편 전 | 최종본 |
| --- | ---: | ---: |
| 전체 재렌더 JS+강제 레이아웃 | 33.45ms | 36.50ms |
| 퀘스트↔마켓 전환 | 33.55ms | 10.85ms |
| 상품 선택 | 2.85ms | 2.00ms |

전체 재렌더는 네 쌍 모두 +1.8~+4.2ms였고 중앙값 기준 +3.05ms 증가했다. 지난 보고의 32.2→35.6ms와 비슷한 방향·크기다. **증가를 측정 편차로만 설명할 수 없다.** 탭 전환과 상품 선택의 개선은 유지됐다.

### 3. CSS/JS 요인 분리, 4개 조합 × 4회

운영 소스를 바꾸지 않고 임시 디렉터리에서 CSS와 교실 render/workspace JS만 교차 조합했다. 데이터·HTML·기타 JS는 같고, 이미지 요청은 로컬 파일로 응답했다. 조합 순서도 바꿨다. 준비 8회 후 20회 측정하며, 아래는 연속 호출 모드다.

| 조합 | JS 중앙값 | 강제 레이아웃 중앙값 | 전체 중앙값 |
| --- | ---: | ---: | ---: |
| 이전 CSS + 이전 JS | 25.10ms | 7.50ms | 32.70ms |
| 이전 CSS + 최종 JS | 26.90ms | 7.80ms | 34.85ms |
| 최종 CSS + 이전 JS | 25.85ms | 8.70ms | 34.45ms |
| 최종 CSS + 최종 JS | 27.20ms | 8.35ms | 35.50ms |

프레임 사이에 한 번씩 실행하는 보조 조건에서도 이전 전체 32.55ms, 최종 35.30ms였다. 단순한 연속 루프에서만 생기는 현상은 아니다. 중앙값끼리의 합과 전체 중앙값은 일치하지 않을 수 있고, 조합 효과도 단순 합산하지 않는다.

판정: 렌더 코드와 CSS/레이아웃 양쪽에서 작은 비용 증가가 확인됐다. 다만 한 함수나 특정 CSS 규칙을 병목으로 단정할 근거는 얻지 못했다. 세부 함수별 임시 계측은 계측 자체가 실행 비용을 크게 바꿔 원인 판정에서 제외했다. 이미지·접근성 기능을 임의로 빼거나 캐시/렌더 범위를 바꾸는 추가 최적화는 하지 않았다. **전체 재렌더 비용 증가는 해결 완료가 아니라 남은 항목이다.**

측정 원본: [measurements/summary.json](../product/classroom-final-review-2026-10-07/measurements/summary.json) 및 같은 폴더의 initial/verified/factor/phase JSON. phase 결과는 위 이유로 최종 수치에 사용하지 않았다.

## 로컬 동작과 실제 초기 로딩의 구분

- 측정한 것: 로컬 데이터가 준비된 상태의 DOM 생성, 강제 레이아웃, 탭 전환, 상품 선택. PNG/WebP 파일 크기와 이미지 표시 크기도 확인했다.
- 측정하지 않은 것: 로그인된 교실의 Firebase 응답 시간, 최초 교실 진입 완료 시간, 실제 네트워크 전송 시간, 실제 휴대전화 FPS.
- `getClassroomEconomyBoard`에는 상태 저장 경로가 있어, 이번 무수정 원칙에 따라 운영 계정으로 호출하지 않았다. 기존 mock 로딩 검사는 실제 서버 속도 측정이 아니다.
- 따라서 “실제 서버 응답/초기 로딩이 빨라졌다”거나 “전체 성능 개선 완료”라고 표현하지 않는다.
