# 분수 월드 이미지 로딩 실측

2026-09-15, 운영 https://dj48-fraction-world.vercel.app/ 읽기 전용 확인. 이번 조사는 코드 수정·배포를 하지 않았다.

## 측정 방법과 한계

새 Chrome 브라우저 컨텍스트, 820×1180 화면, DPR 2, CDP 다운로드 5Mbps·지연 40ms 조건. 첫 화면 → 시작 무기/옷 선택 → 지도 → 첫 지역 전투 순서로 진행했다. 단계별 필수 이미지의 Resource Timing 완료를 기다리고 안정화 대기 약 0.8초를 포함했다. 아래 시간은 화면 조작이 불가능한 시간이 아니라 이미지가 모두 준비될 때까지의 측정 구간이다. 실제 학생 태블릿·학급 무선망 측정값은 아니다.

| 단계 | 새 이미지 전송량 | 이미지 준비 확인 구간 |
| --- | ---: | ---: |
| 첫 로비 | 6.27MiB | 11.97초 |
| 시작 무기·옷 선택 | 8.10MiB | 14.98초 |
| 첫 지도 | 5.69MiB | 10.66초 |
| 첫 전투 | 4.46MiB | 8.39초 |

첫 전투까지 누적 약 24.52MiB. 원본 assets 폴더는 약 43MiB지만 전부가 첫 화면에 다운로드되는 것은 아니다. MiB는 1,048,576바이트다.

다시 로비를 열었을 때 약 1.09초, 탑으로 재진입했을 때 약 0.86초. 재진입 시 무기 선택 화면의 이미지 리소스가 관측됐으므로 이를 전투 재개 시간으로 해석하지 않는다. 이미지 본문 추가 전송은 관측되지 않았고, 대부분 캐시 재검증 응답 약 300바이트를 받았다. `encodedBodySize`는 캐시된 원래 용량을 나타낼 수 있어 본문 전송량 계산에는 실제 `transferSize`를 사용했다.

## 원인

1. `pixel-combat-art.js`가 실행 즉시 네 무기 계열 시트를 모두 요청한다. 약 5.01MiB이며 로비의 표지와 대역폭을 나눠 쓴다. 사용하지 않는 무기 기술까지 첫 화면에서 읽는다.
2. 시작 선택 화면은 무기 시트 2장과 모험가 시트 2장, 총 약 8.10MiB를 받는다. 지도·시설 시트는 약 5.69MiB다. 작은 아이콘을 위해 여러 그림이 합쳐진 대형 PNG 전체를 다운로드한다.
3. 실제 요청된 큰 파일: `maps-v4.png` 2.99MiB, `explorers-v4.png` 2.75MiB, `locations-v4.png` 2.69MiB, `weapons-v4.png` 2.31MiB, `weapons-v2.png` 2.05MiB.
4. 전투 이미지는 렌더링할 때 처음 요청한다. 원본 준비 전에 대체 그림을 그리며, 대체 캐릭터용 `actors-v1.png` 2.12MiB까지 추가 요청되는 것을 확인했다. `monsters-v6.png` 1.77MiB는 적이 등장한 뒤 요청된다. 이미지 다운로드 중에도 전투가 진행될 수 있다.
5. 실제 응답의 `Cache-Control`은 `public, max-age=0, must-revalidate`다. Vercel CDN HIT여도 사용자 브라우저는 재접속 시 서버 확인을 한다. 이는 매번 전체 파일을 다시 받는다는 뜻은 아니다. 첫 접속의 주요 문제는 파일 용량과 요청 순서다.
6. 원본 PNG 다수가 약 157만 픽셀이며 풀어 놓으면 장당 약 6MiB다. 다운로드 압축만으로 디코딩 메모리까지 감소하지는 않는다.

## 다운로드 이후 CPU 처리 확인

별도 비제한 Chrome 측정에서 `createImageBitmap(blob)` 디코딩은 지도 34.3ms, 모험가 29.0ms, 수호자 기술 시트 19.9ms였다. 네 프레임 × 무기 12종의 첫 기술 이미지 가공은 92.5ms, 캐시 재사용은 0.2ms였다. 현재 `cel()`은 처음 사용할 때 알파 픽셀을 순회해 그림 영역을 찾는다. 이 수치를 매 기술마다 92.5ms가 걸린다고 해석하면 안 된다. 낮은 사양 기기에서는 첫 기술 사용 때 순간 끊김의 원인이 될 수 있다.

## 수정 우선순위

1. 첫 로비의 무기 기술 시트 전체 선로딩 제거. 선택한 무기·필수 받아치기 효과만 준비하고 다음 화면에 필요한 것을 문제 풀이 중 미리 요청한다.
2. 이미지 용량 최적화: 투명도와 도트 경계를 보존하는 WebP 및 실제 표시 크기에 맞는 시트/썸네일. 크롭 좌표에 원본 픽셀 크기가 쓰이므로 일괄 축소 후 경로만 바꾸면 안 된다. 캐릭터와 기술의 잘림·투명 영역 검증 필요.
3. 전투 시작 전에 캐릭터·선택 무기·지역 바닥·몬스터의 로딩/디코딩을 완료하고 준비 상태 표시. 완료 전 전투 타이머를 돌리지 않는다. 미준비 상태에서 큰 레거시 시트를 추가 다운로드하는 대체 경로 제거.
4. 콘텐츠 해시/새 버전 URL의 이미지에 장기 캐시 적용. HTML/스크립트 갱신 정책과 구분하며 기존 파일 URL을 덮어써 영구 캐시가 남지 않도록 한다.
5. 기술 프레임의 알파 영역 좌표를 사전 계산해 런타임 전체 픽셀 순회를 줄인다.

결론: 앞선 DOM·음악 부하 수정은 이미지 다운로드 문제를 해결하지 않았다. 이미지 전송량과 로딩 순서를 우선 보완해야 한다.
